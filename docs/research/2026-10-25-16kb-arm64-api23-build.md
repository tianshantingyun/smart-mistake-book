# 16KB / arm64 / API23 构建面研究（R4 → T8）

- 日期：2026-10-25（R4 研究线，批次 20）
- 作者：R4 构建面研究（本机实测 + 官方文档核对）
- 结论消费者：T8（16KB/arm64 构建配置与 .so 对齐核查）、R1（QuickJS 选型的 16KB 证据）、设备轨（x86_64 装载验证）
- 本文所有"实测"均在 2026-10-25 于本机（Windows/Git Bash，SDK=C:\Android\Sdk）执行，命令可原样复跑。

## 0. 结论摘要（TL;DR）

1. **ZIP 层已合规**：现有 debug/release APK `zipalign -c -P 16 4` 全过，21 个 `.so` 条目全部 STORED 且 `data_offset % 16384 == 0`——AGP 9.3.0 已自动做 16KB ZIP 对齐，**gradle 侧无需任何打包属性改动**。
2. **ELF 层：arm64-v8a 与 x86_64 两个 64 位 ABI 全部合规**（含 litert 三件套、ML Kit、androidx）。**唯一不合规的是 ML Kit 的 32 位 `.so`**（`text-recognition-bundled-common:17.0.0` 的 armeabi-v7a 3 个 LOAD、x86 4 个 LOAD 仍为 p_align=4096；x86 的 RELRO 还与可写段同页）。而 Maven 实测该 artifact 已是最新版 → **没有升级路径，只能裁 ABI 或接受**。
3. **quickjs-kt 1.0.15 发布 AAR 的 4 个 ABI 全部合规**（PT_LOAD 16384 + RELRO 独占 LOAD 段）。这与 `.jez/artifacts/android-visual-runtime-probe-2026-10-17/research-findings.md` 的"RELRO 未对齐=不合格"结论**相反**：探针没应用官方页面的"GNU_RELRO 独占 LOAD 段时非零余数仍合规"豁免；本机复测的余数与探针逐字一致（arm64 余 4096、x86_64 余 12288），判读差异纯在判据。R1 可据此重新权衡"源码重建 vs 直接用 AAR"（对齐维度 AAR 已达标；其余维度仍归 R1 裁）。
4. **Play 政策**：targetSdk 35+（本项目 36）必须在 64 位设备支持 16KB；**2027-02-01 起不支持的更新将无法发布**（官方页现行口径；自 2025-11-01 顺延，见 §1.1）。15 个月窗口，非紧急但 T8 本批即可低成本收口。
5. **推荐配置改动只有一处**：`app/build.gradle.kts` defaultConfig 加 `ndk { abiFilters += setOf("arm64-v8a", "x86_64") }`（消灭 §2.3 表中唯一的违规项 + 裁掉本就不完整的 x86 半 ABI + 省 ~23MiB 未压缩 .so；代价是放弃纯 armv7 设备 → 产品裁定项，见 §5）。
6. 本机**无 NDK**（`C:\Android\Sdk\ndk` 不存在）→ 官方 `llvm-objdump` 法本机跑不了；本文用等判据 Python 脚本替代（§6.2，脚本内嵌可复跑）。若 T4 走源码重建需装 NDK r28+。
7. 模拟器：本机两个 AVD 均为 android-34 x86_64 google_apis = **4KB 页**，测不了 16KB；16KB 图像包 `_ps16k` 已实测可下载（API 35–37.2，arm64+x86_64 双架构，§4.2 给命令）。

## 1. 官方要求（引文级核对，2026-10-25 抓取）

主源：`https://developer.android.com/guide/practices/page-sizes`（本轮 webReader 全文抓取成功；WebFetch 对 developer.android.com 超时，已换通道）。

### 1.1 Play 政策与时间线

> "all apps targeting Android 15 (API level 35) and higher must support 16 KB memory page sizes **on 64-bit devices** on Google Play. Starting **February 1, 2027**, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates."

- 要求对象 = targetSdk 35+（本项目 targetSdk=36，命中）且限于 64 位设备。
- 2027-02-01 为"更新无法发布"的硬线；原口径 2025-11-01，后有顺延（r/androiddev 2026 年讨论佐证官方页现行日期；社区来源，仅作旁证）。
- 设备侧存在 **16KB 兼容模式**：`.so` 只有 4KB LOAD 对齐（或未压缩 .so 仅 4KB ZIP 对齐）时，系统可让 app 以兼容模式跑（官方页"16 KB backcompat"段）。官方页**未按 ABI 区分**该判定 → APK 里带 4KB-only 的 32 位 `.so` 是否会让整个 app 在 16KB 真机进兼容模式，官方口径不明确，标注**待验证**（§7-2；若采纳 §5 的 abiFilters 则该问题整体消失）。

### 1.2 AGP 版本线（ZIP 层）

官方页"Build your app with the 16 KB alignment"节：

- **AGP ≥ 8.5.1 + 未压缩共享库** → ZIP 层 16KB 对齐（本项 AGP 9.3.0 ✓，且 §2.1 已用实物 APK 验证）。
- AGP ≤ 8.5 → `useLegacyPackaging = true`（压缩式打包，页对齐不适用）。
- AGP ≤ 8.0 还需 `android.bundle.enableUncompressedNativeLibs=false`（默认改过）。
- 本项目不落任何一条：9.3.0 已在线上，且实测合规。

### 1.3 NDK 版本线（ELF 层）

- **NDK r28+（2025-02-19 稳定）默认产出 16KB 对齐 ELF**；`llvm-readelf` 增强为可显示默认对齐。
- **NDK r27 及以下**需显式链接旗标：`-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384`。
- `PAGE_SIZE` 宏自 r27 起未定义（16KB 开启时）→ 代码应改用 `sysconf(_SC_PAGESIZE)`。
- r29（2025-10-21）当前最新，不改变以上口径。（源：NDK 修订历史页 `developer.android.com/ndk/downloads/revision_history`，本轮 webReader 抓取。）
- 本机无 NDK；本项目无自研 JNI 源码（所有 `.so` 来自 AAR）。若 T4 源码重建 QuickJS：`sdkmanager "ndk;28.2.13676358"`（r28 系具体版本号装时再核）。

### 1.4 zipalign（ZIP 层核查）

- 核查命令：`zipalign -c -P 16 -v 4 APP.apk`；`-P` = page alignment，要求**未压缩 `.so` 条目的 ZIP 偏移 16KB 对齐**；`-P` 需要 **build-tools ≥ 35.0.0**（官方页注明）。
- 本机 build-tools 36.0.0/37.0.0 均含 `zipalign.exe`（实测 `ls`）；37.0.0 已实测可用（§2.1）。

### 1.5 ELF 对齐判据（官方，含关键豁免）

官方页"Check ELF alignment using command-line tools"：

1. 每个 `PT_LOAD` 的 `p_align` 必须 **≥ 2**14 (16384)**。检查：`llvm-objdump -p FILE.so | grep LOAD`（需 NDK；build-tools ≥35 才带对的 llvm 工具）。
2. **RELRO**：`PT_GNU_RELRO` 段终点 `(VirtAddr + MemSiz) % 0x4000 == 0`——**但官方明确豁免**："If the GNU_RELRO segment is in its own LOAD segment, the non-zero value returned is still compliant"（RELRO 独占一个 LOAD 段、其后同 16KB 页内无可写数据时，非零余数合规）。违规形态 = RELRO 终点后同页出现可写段（官方示例：RW 段 VirtAddr 落在 RELRO 余数页内 → "in violation"）。运行时后果 = 16KB 设备上 linker 的 RELRO mprotect 把整个 16KB 页变只读 → 后续写 .data SIGSEGV。

> 本机无 NDK 无 llvm-objdump → §6.2 的 Python 脚本按上述两条判据 + 豁免逻辑直接解析 ELF 程序头，输出与官方 `check_elf_alignment.sh` 同判。这是替代工具，判据同源（脚本内嵌于本文，可复跑）。

## 5. 配置改动清单（gradle 侧，供 T8）

按"每项指认它消灭哪个已有失败"：

1. **`app/build.gradle.kts` defaultConfig 加（推荐）**：
   ```kotlin
   ndk { abiFilters += setOf("arm64-v8a", "x86_64") }
   ```
   消灭：① APK 内唯一 16KB 违规（mlkit 32 位 `.so` 的 4KB LOAD，§2.3）；② x86 残缺 ABI（litert 缺席）持续入包；③ ~23 MiB 未压缩 32 位 `.so` 死重。Play 要求只针对 64 位设备（§1.1），裁 32 位不损合规面。
   **代价（产品裁定项，T8 呈报后落）**：纯 armv7 32 位真机（Android 6–11 时代低端机）无法安装。minSdk 23 名义上覆盖的机型面会收窄到 64 位设备。若用户要求保 armv7：备选 = 不裁 ABI、依赖"32 位库在 64 位设备不装载"的事实接受现状，但 §1.1 的兼容模式歧义（app 是否因 32 位 4KB ELF 进兼容模式）必须先在 ps16k 模拟器实测（§7-2）。
2. **不加** `useLegacyPackaging`/`enableUncompressedNativeLibs`/任何 zipalign 配置——AGP 9.3.0 已实测自动合规（§2.1/2.2），加配置不消灭任何失败。
3. **不动** litert 2.1.6 钉版——其 64 位 `.so` 已合规（§2.3）；升级线被 minSdk 24 锁死（§2.5），与 16KB 无关。
4. **T4 若走源码重建 QuickJS**：先 `sdkmanager` 装 NDK r28+（本机无 NDK，§2.1）；若 R1 最终采用 quickjs-kt 1.0.15 AAR，则对齐维度零改动（§2.4）。
5. **设备轨（随 T8/设备窗口）**：装 ps16k 图像 + 建 AVD + `getconf PAGE_SIZE` 断言 + 装载冒烟（命令见 §6.3）。

### 6.2 ELF 层（本机替代工具 = 官方判据；NDK 装好后可换 llvm-objdump 复核）

脚本一 `check_elf_alignment.py`（判据：PT_LOAD p_align≥16384 且 offset/vaddr 同余；RELRO 终点 16KB 整倍数**或**余数页内无可写 LOAD 段 = 官方"独占 LOAD"豁免；ELF32/64、大小端通吃）：

```python
#!/usr/bin/env python3
import struct, sys
PT_LOAD, PT_GNU_RELRO = 1, 0x6474E552
def check(path):
    data = open(path, "rb").read()
    if data[:4] != b"\x7fELF": print(f"FAIL  {path}: not ELF"); return False
    is64, little = data[4] == 2, data[5] == 1
    end = "<" if little else ">"
    if is64:
        e_phoff = struct.unpack_from(end+"Q", data, 0x20)[0]
        e_phentsize = struct.unpack_from(end+"H", data, 0x36)[0]
        e_phnum = struct.unpack_from(end+"H", data, 0x38)[0]
        ph = end+"IIQQQQQQ"  # type, flags, offset, vaddr, paddr, filesz, memsz, align
    else:
        e_phoff = struct.unpack_from(end+"I", data, 0x1C)[0]
        e_phentsize = struct.unpack_from(end+"H", data, 0x2A)[0]
        e_phnum = struct.unpack_from(end+"H", data, 0x2C)[0]
        ph = end+"IIIIIIII"  # type, offset, vaddr, paddr, filesz, memsz, flags, align
    ok, loads, relros = True, [], []
    for i in range(e_phnum):
        f = struct.unpack_from(ph, data, e_phoff + i*e_phentsize)
        if is64: t,_fl,off,va,_pa,_fs,msz,al = f
        else:    t,off,va,_pa,_fs,msz,_fl,al = f
        if t == PT_LOAD: loads.append((off,va,msz,al,bool(_fl & 2)))
        elif t == PT_GNU_RELRO: relros.append((va,msz))
    name = path.split("/")[-1]
    for i,(off,va,msz,al,w) in enumerate(loads):
        s = "PASS" if al >= 16384 else "FAIL"
        ok &= al >= 16384
        print(f"{s}  {name} LOAD#{i}: p_align={al} (0x{al:x}) congruent={off%al==va%al if al else False}")
    for rva,rmsz in relros:
        rend = rva+rmsz; rem = rend % 16384
        if rem == 0: print(f"PASS  {name} RELRO end=0x{rend:x} mod=0"); continue
        page_end = (rend+16383)//16384*16384
        clash = [hex(v) for (_o,v,m,_a,w) in loads if w and v < page_end and v+m > rend]
        if clash: ok = False; print(f"FAIL  {name} RELRO end=0x{rend:x} mod={rem} writable-in-page {clash}")
        else: print(f"PASS  {name} RELRO end=0x{rend:x} mod={rem} own-LOAD (compliant)")
    return ok
sys.exit(0 if all(check(p) for p in sys.argv[1:]) else 1)
```
