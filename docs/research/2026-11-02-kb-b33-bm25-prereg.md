## 1. 机制（冻结）

### 1.1 公式与参数

词面腿分数由 `COUNT(DISTINCT feature)` 改为 **FTS5 等价 BM25**。**冻结形式**（与 r1:110-118 的 `fts5_aux.c` 逐项对应）：

```text
bm25FTS5(n) = − Σ_{f ∈ M(n)}  IDF(f) · f(q,D)·(k1+1) / ( f(q,D) + k1·(1 − b + b·|D(n)|/avgdl) )

IDF(f)      = ln( (N − df(f) + 0.5) / (df(f) + 0.5) )        ，若 IDF(f) ≤ 0 则取 1e-6
k1          = 1.2        （写死）
b           = 0.75       （写死）
f(q,D)      = 1          （每个匹配特征只计一次，见下）
|D(n)|      = len(n)     = 该节点在 knowledge_search_feature 的全部行数
avgdl       = 全语料特征行数 / N
N           = 被索引节点数（有 ≥1 行特征的节点）
df(f)       = 含特征 f 的被索引节点数（跨科全局）
```

**`tf ≡ 1` 的依据**（不是假设）：特征表主键 `(subject, search_feature, knowledge_node_id)`（schema 73 `createSql` 实读），同一 (节点, 特征) 只可能有一行；因此 `/ (f + k1·(…))` 的分母首项恒为 1，公式退化为：

```text
bm25FTS5(n) = − Σ_{f ∈ M(n)} IDF(f) · 2.2 / ( 1 + 1.2·(1 − 0.75 + 0.75·len(n)/avgdl) )
```

**四个冻结细节（逐条对应 r1）**：

1. **IDF 不带 `+1`**（r1:122）。这是与 L1 唯一的实质公式差异，也是本预注册存在的理由（§0.4）。
2. **`IDF ≤ 0` 钳到 `1e-6`**（r1:103、123），**逐特征、求和前**施加。`df = 0` 的特征不参与任何节点（没有行可匹配），**不计算、不钳位**。
3. **`N` / `avgdl` / `len` 的域都是“被索引节点全集”**（4 科全局），**不是**本次查询的候选域；`len(n)` 是该节点**全部**特征行数，不是匹配数。统计域与召回 SQL 的过滤域逐条一致：`verification_status IN ('CURATED','SOURCE_GROUNDED','USER_CONFIRMED')` 且 `status != 'RETIRED'`（与 `ProblemOrganizationDao.kt:217-218` 逐字相同）。特征行只为该域节点写入、退役即删行（`countIndexedKnowledgeNodesBySubject` 的 KDoc 已把这条列为不变量），执行轮用 §3.5 的 DB 计数复核，不用“过滤条件重复写一遍”来买成本。
4. **`k1` / `b` 禁止网格搜索**，不得按结果回调；`N` / `avgdl` 不得写死人肉常数。

### 1.2 符号与排序方向（冻结，防写反）

FTS5 的 `bm25()` 返回**负值**、**越负越好**（r1:107：`sqlite3_result_double(pCtx, -1.0 * score)`）。本仓的词面分进入 `DenseFusion` 时是**越大越好**（`DenseFusion.minMax` 把 `low→0`、`high→1`，`DenseFusion.kt:24-34`）。因此冻结两个量并写死用途：

| 量 | 定义 | 用途 |
|---|---|---|
| `bm25FTS5(n)` | §1.1 的带负号形式（≤ 0，越负越好） | **只**用于与 SQLite `bm25()` 对拍、以及排序的等价性说明（`ORDER BY bm25FTS5 ASC` ⇔ `ORDER BY s DESC`） |
| `s(n) = −bm25FTS5(n)` | `= Σ IDF·2.2/(1+k1(…))`（≥ 0，越大越好） | **唯一**进入 `lexicalScore` / `DenseRecallCandidate` / `DenseFusion` 的值；词面腿自身也按 `s` 降序 |

- **不得**把 `bm25FTS5` 的负值直接交给 `DenseFusion`：min-max 在取负下变成 `1 − norm`，词面腿的优劣会**整体反相**（最差的候选拿 1.0）。这是本臂最容易犯且最难从聚合指标看出来的错误，故单列。
- 排序键（全序，与现行逐条同序，只换首键）：

```text
s DESC, CASE granularity WHEN 'ATOMIC' THEN 0 ELSE 1 END, canonical_name ASC, knowledge_node_id ASC
```

- 512 深度仍按新分数截断（`StudyDatabasePort.kt` 的 `MAX_KNOWLEDGE_RECALL_CANDIDATES`，L2:211 引为 512，**本臂不改**）；候选成员会随分数定义变化——这是机制的一部分，不是漂移（r1:297；L1:180）。

### 1.3 数值确定性（零漂移的前提）

1. **IDF 用 `java.lang.StrictMath.log`**，两端同一调用；`Math.log` 允许平台 1 ulp 差异，足以在并列处翻转名次（L1:103 已登记同类风险）。
2. **IDF 求和按特征串的 Kotlin 自然序（UTF-16 code unit）排序后累加**，两端（设备 Kotlin / JVM 镜像）都用同一个 `sorted()`，因此求和顺序与 SQL 的 `GROUP_CONCAT` 顺序、集合迭代顺序无关，**逐位可复现**。这是对 L1 定点方案的替代（§0.4），不留量化误差。
3. **表达式树写死，两端逐字相同**（不得改写结合顺序）：

```text
ratio = len.toDouble() / avgdl
den   = 1.0 + 1.2 * (1.0 - 0.75 + 0.75 * ratio)
s     = idfSum * ((1.2 + 1.0) / den)          // idfSum = Σ_{f ∈ sorted(M(n))} idf(f)
idf   = StrictMath.log(((n - df).toDouble() + 0.5) / (df.toDouble() + 0.5))   // 商再取对数，见第 4 条
```

4. **IDF 的写法**：`ln((N−df+0.5)/(df+0.5))` 与 `ln(N−df+0.5) − ln(df+0.5)` 在实数上相等、在浮点上**不一定**逐位相等。为让两端与 §7 的手算脚本可比，**冻结为商再取对数**：`StrictMath.log(((n - df).toDouble() + 0.5) / (df.toDouble() + 0.5))`；`n`、`df` 为 `Int`，先转 `Double` 再加减，避免整型截断。**不得**用两对数相减的等价写法。
5. 不使用 SQL 的 `ln()`/`log()`：API 23 的 framework SQLite 不保证数学函数（r1:279、319）；IDF 与最终分数都在 Kotlin 算。
6. 定点量化**不采用**（与 L1 不同）：确定性由“整数输入 + 严格排序求和 + 同一表达式树”保证；§7 用手算脚本对拍 `s` 与 `bm25FTS5`（转负号），容差 0。

### 1.4 查询路径（冻结顺序）

`RoomKnowledgeBaseStore.readSubjectKnowledgeRecallCandidates` 内，`ensureKnowledgeSearchIndex(subject)` 之后，**在同一个 `withReadTransaction` 快照里**依次执行（顺序不可换、不可拆到不同事务）：

1. **df 查询**（§2.1）：对**本次查询的 128 特征**求全局 df；
2. **语料统计查询**（§2.2）：求 `N`、`totalRows`、`avgdl`；
3. **匹配集查询**（§1.4.1）：求每节点的 `matchedFeatures`（`GROUP_CONCAT`，分隔符 `CHAR(31)`）与 `len`（相关子查询 `COUNT(*)`），**不带 `ORDER BY`、不带 `LIMIT`**；
4. **Kotlin 打分与定序**：§1.3 的表达式树 → §1.2 的排序键 → `take(limit)`（512）；
5. 之后原样进入 `rerankMatchOrder` / `DenseRecallCandidate` / 父节点补全。

- **为什么同一读事务**：df、len、N 与候选集必须来自同一快照；否则并发重建/退役会让 IDF 与候选集错位（候选里出现 df 未计的行，或反之），排序仍然“看起来正常”。这是新增的一次事务边界，消灭的是一次具体的读偏斜。
- **为什么去掉 SQL 的 `ORDER BY`/`LIMIT`**：`|D(n)|/avgdl` 与 `Σ IDF` 都是节点级量，SQL 里没有 IDF（不能调 `ln()`）也没有跨特征的和；把定序放 Kotlin 是零 schema 下的唯一精确解法。代价是候选集不再被 SQL 截断——本臂实测匹配节点 p50 308 / p95 647 / max 845（§2.3），全量打分后 `take(512)` 与“SQL 先取 512 再打分”**不等价**，本臂明确选前者（精确 BM25 top-512），并把成本记在 p95 门里。

#### 1.4.1 匹配集 SQL（冻结形状；Room 若拒绝 `GROUP_CONCAT` 的 bare column，改用 `@RawQuery` 同 SQL，语义不变）

```sql
SELECT node.*,
       GROUP_CONCAT(feature.search_feature, CHAR(31)) AS matchedFeatures,
       (SELECT COUNT(*) FROM knowledge_search_feature AS len_row
         WHERE len_row.knowledge_node_id = node.knowledge_node_id) AS featureCount
FROM knowledge_search_feature AS feature
INNER JOIN knowledge_node AS node
  ON node.knowledge_node_id = feature.knowledge_node_id
WHERE feature.subject = :subject
  AND feature.search_feature IN (:searchFeatures)
  AND node.verification_status IN ('CURATED', 'SOURCE_GROUNDED', 'USER_CONFIRMED')
  AND node.status != 'RETIRED'
GROUP BY node.knowledge_node_id
```

- `matchedFeatures` 的**行内顺序不承诺**（SQLite 未定义 `GROUP_CONCAT` 顺序）；Kotlin 侧一律 `split('\u001F').sorted()` 后再求和（§1.3-2），所以顺序不影响结果。
- `featureCount` = `len(n)`，按 `index_knowledge_search_feature_knowledge_node_id` 点查（schema 73 已存在，**不新建索引**）。

### 1.5 每一项新增消灭的具体失败（逐个指认）

## 2. df 来源与成本（零 schema）

### 2.1 df：查询期、候选特征、无统计表

**冻结查询**（一个 DAO 方法，一条 SQL）：

```sql
SELECT search_feature, COUNT(DISTINCT knowledge_node_id) AS df
FROM knowledge_search_feature
WHERE subject IN (:subjects)
  AND search_feature IN (:searchFeatures)
GROUP BY search_feature
```

- `:searchFeatures` = **本次调用传入的同一个查询特征集**（`KnowledgeSearchFeatureExtractor.fromQuestion` 的结果，≤128），不扩张、不改写、不追加别名。
- `:subjects` = **4 个包内科目**，顺序写死 `MATH, PHYSICS, CHEMISTRY, BIOLOGY`；df 是**跨科全局**（L1:94 的口径保留），不是单科。包外 subject 的行**按定义不属于 KB 语料**，不计入 df/N（§7 报告 DB 里是否另有 subject 行）。
- **不建**：`knowledge_search_feature_df`、`knowledge_search_df_idf`、`knowledge_search_node_len`、`knowledge_search_corpus_stat`；**没有** `stale` 脏标记，**没有**导入期统计、**没有**写路径维护点。L1 §1.4 的 4 张表与 5 个维护点全部作废（§0.4）。
- df 用现有主键前缀 `(subject, search_feature, …)`，**不新增索引**（r1:280）。
- df 与匹配集、语料统计在**同一读事务**内取（§1.4），防止快照错位。

### 2.2 N / avgdl / len 的来源（全部查询期现算）

```sql
-- N 与 totalRows：4 科全集，一次聚合
SELECT COUNT(DISTINCT knowledge_node_id), COUNT(*)
FROM knowledge_search_feature
WHERE subject IN (:subjects)
```

- `len(n)` = §1.4.1 的 `featureCount`（节点全部行数，与本次匹配无关）。
- **可复算基准**（写前实读）：v27 冷启同一日志 `N = 3,718`、`totalRows = 546,872`、`avgdl = 147.0877`。执行轮**以 DB 实测为准**并写 §7；若与这组值不等，先解释节点集/内容代际差，不得直接判 `CORPUS_MISMATCH`。

`Bm25MirrorParityTest`（JVM，`core/data/src/test/.../knowledge/`）必须覆盖：

1. **手算对拍**：给定小夹具（N、每节点 len、每组 df），用测试内**独立**写的 `exp/log` 式子算 `s`，与 `KnowledgeSearchBm25.score` 容差 0 相等；
2. **钳位**：`df > N/2` ⇒ 该特征 IDF = `1e-6`（不是 0、不是负）；
3. **无 `+1`**：同一组 (N, df) 与 Lucene(+1) 变体给出**不同**的 IDF 和，并断言镜像取无 `+1` 的那个（用 r1:129-136 的 A/B 反例做固定用例：SQLite 口径 B 高、Lucene 口径 A 高）；
4. **求和顺序无关**：把同一节点匹配特征以两种顺序喂入，分数**逐位相等**（排序求和的验收）；
5. **`s = −bm25FTS5`**：`bm25FTS5` 的排序与 `s` 的排序严格相反，且 `s ≥ 0`。
