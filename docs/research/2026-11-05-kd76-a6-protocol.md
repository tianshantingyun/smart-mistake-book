## 0. 结论（pick）

1. **A6 的准确形状是"两次各自完整的 n=20 判词"，不是"10+10 合并 n=20"。** 每批独立走单轮入口 `readRoundFromInstrumentationArg`（`VisualJsConnectStageCalibrationInstrumentedTest.kt:296-380`）+ `run_kd76_rounds.sh`（每轮一次 reboot + 一次独立 `am instrument`）+ `summarize_kd76.py`（每批 n=20、G1/G2 独立判定）。A6 = **两批都 PASS 且跨批独立性检查全绿**；不是把 40 个样本并成一个 n=40。
2. **A6 的"独立"是操作独立，不是概率独立。** 两批共享同一设备、同一构建、同一宿主；不能做 iid 推断、不能把两批当独立同分布样本算合并分位数。A6 是**可复现性合取**（anti-flaky），不是显著性检验。
3. **必须同时锁六类代际**：构建代际（app/test APK 字节）、安装代际（firstInstallTime/lastUpdateTime/签名）、设备代际（serial/fingerprint/sdk/abis/pageSize/build.id/AVD/模拟器实例）、启动代际（`boot_id` + `bootCount`）、进程代际（每轮 `:visual_js` 冷、`generation` 过滤生效）、证据代际（`runId` + 文件哈希链）。任一跨批不等 → A6 NOT EVALUABLE。
4. **时间分离 = 结构非重叠 + 严格顺序 + 预注册间隔。** 硬性：A 批全部轮次窗口严格早于 B 批、无任何轮次窗口重叠；B 批首轮 boot_id 不在 A 批集合内。策略：预注册 `minSeparationMinutes`（建议 30，硬下限 10；本项目设计裁定，不是外部统计定理）。
5. **`boot_id` 是 40 轮"各自一次新 boot"的主证明；`bootCount` 是副证明。** 40 个宿主 `boot_id` 必须两两不同、A∩B=∅、每轮 before==after；app `bootCount` 非空、与宿主一致、跨批严格递增。`force-stop`、`adb reboot userspace`、`stop && start`、快照/quick boot 都会保留同一 `boot_id`，一律出局。
6. **G1/G2 只在批级判定，A6 只做合取。** 批级 G1 绿（n=20、无 FAIL/INVALID/XML failure）+ G2 绿（nearest-rank p95 ≤ 5000 ms）→ 该批 PASS；任一批 G1 红/样本不足 → A6 NOT EVALUABLE；两批 G1 绿但任一批 G2 红 → A6 REFUTED。**G1 红不等于"没失败"**：失败轮若归因产品，台账必须另记真红。
7. **合并规则禁相加。** 禁止 n=40、禁止合并原始样本算 p95、禁止平均/相加两批 p95、禁止把 `max(p95A,p95B)` 当"合并 p95"（它可以作为"较差批"的描述，但门仍是两个独立门）。本轮探针：A p95=318、B p95=518、合并 n=40 p95=517、两批 p95 平均=418——三个数互不相等；n=40 的 p95 是第 38/40 个，**容忍 2 个最大值**，而 n=20 只容忍 1 个，合并会静默放宽预注册。
8. **当前工具不能判 A6。** `summarize_kd76.py` 把两批目录一起传 → 轮号重复 `exit=2`；把 B 改号 21..40 → `unexpected round ids` `exit=2`；分开传则**没有任何跨批检查**。而且最小手写 XML（无 `am instrument` 输出、无墙钟时间戳）实测可 `G2: PASS`——门只信 XML 文本。必须先补跨批 composer 与证据链，才能谈 A6。
9. **批次 42 的两次 n=20 不是 A6。** 两批各自 PASS（p95 1889 / 1969 ms），bootCount 3..22 / 24..43、时间相隔约 9 h 23 min，但 app sha `35e10339…` ≠ `ec135844…`、test sha `0e906482…` ≠ `a2532e16…`——**构建代际不同**，不能作为"同一构建两次独立"的关闭证据。
10. **A6 只覆盖测试进程口径，不覆盖 C4/29.5 s 链/arm64/真机。** 即使 A6 CONFIRMED，KD-76 仍不能单独关闭：C4（产品进程首请求）、29.5 s 四段、arm64/真机、低内存仍是 UNVERIFIED/BLOCKED（§9）。A6 的 PASS 不能写成"用户首请求已达标"。

## 1. 定义与范围

### 1.1 A6 在 KD-76 里的位置

- R2 的 anti-flaky 第 6 条：**"两轮独立——关闭/维持证据要求两批独立冷启动均过 G1/G2"**（`docs/research/2026-11-01-kd76-stats.md:235`）。
- R2 的样本量条：默认"两批独立冷启动各 10 轮、合并原始样本 n=20"（同上 `:12,75`）。这是**单次门**的样本形状；A6 要求的是**两次完整的门判定**。
- 批次 43 计划把 A6 升级为"同构建两次独立 **20** 轮、两次样本独立判词（各自 n/p95/G1/G2），不合并 n"（计划 `:39-40`）。理由：批次 42 已有单批 n=20；A6 缺的是**第二个完整 n=20 判词**，不是把 n 从 20 加到 40。
- 单轮入口的 `CALIBRATION_ROUNDS=20` 是**预注册样本量**（两条入口共用）；`BATCH_SIZE=10`（`VisualJsConnectStageCalibrationInstrumentedTest.kt:1079-1080`）只属于**旧单进程 20 轮入口**的内部分批，不是主口径的 A6 形状。主口径走单轮入口，每轮 `-e smb.kd76.round N`，N ∈ 1..20；两者不冲突，但台账不得拿 `BATCH_SIZE=10` 来论证 A6。

### 1.2 本协议回答什么

1. 两次 20 轮在什么条件下才算"独立"（时间、进程、设备、boot、证据）。
2. 每批怎么判、两批怎么合成 A6 判词（含真值表与退出码）。
3. 哪些"合并"是禁止的，为什么。
4. 哪些点可以被伪造/漂移，当前工具能抓哪些、抓不到哪些、需要什么补强。

### 1.3 本协议不回答什么

- 不重新定义 M、p95、门（沿用 `M = S-bind + S-warmup`、nearest-rank、5000 ms）。
- 不改 `READY_TIMEOUT_MILLIS=10_000`、不改 5000 ms 门、不放宽断言。
- 不覆盖 C4（产品进程/UI 首请求）、29.5 s 链、arm64/真机、低内存。
- 不把 A6 写成统计保证；n=20 的 observed p95 不是"真 p95 已证明"。

## 3. 独立性的操作定义（六类代际 + 时间分离）

> 以下 `I0–I10` 是 A6 composer 必须检查的项。任何一项红 → A6 NOT EVALUABLE（不是 REFUTED）。理由码写在括号里。

### 3.1 构建代际（`build_mismatch`）

- **同一构建 = 已安装的 app APK 字节相等 + 已安装的 test APK 字节相等**，不是 `sourceHead` 相等、不是 `versionName` 相等、不是同一次 Gradle 任务名。
- 主锚：宿主用 `pm path` 拉取**已安装** base APK 并算 sha256（仓库已有 `installed_apk_identity()`，`tools/ci/t4_control_marker.py:192-233`）；test APK 同法。
- **per-round `KD76_META apkSha256` 是 app 自报值，不能作为唯一锚**：它可能缺失，也可能被手改；A6 的构建代际锚必须是宿主拉取的已安装 sha，app 自报值只作交叉。现有 per-batch 工具只看 app 自报 sha（`summarize_kd76.py:508-514`），这是 A6 必须补的缺口。
- 两批的 `installedAppSha256`、`installedTestSha256` 必须相等，且等于预注册 `a6-plan.txt` 的 `expectedAppApkSha256` / `expectedTestApkSha256`，且等于构建产物 sha（若传了 `--apk`）。
- `sourceHead` / `sourceDirtyPaths` 只作审计元数据：不同不直接判红，但要在报告里并列；若 APK sha 不同，source 相同也判红。
- **消灭的失败**：批次 42 的两次 n=20 用同 HEAD、不同 APK，被误当成 A6。
- 原则上"同一构建"可以是历史 APK（只要两批都用它并通过 I0–I10）；但历史批通常缺 `runId`/安装代际/逐轮墙钟，默认不满足 A6 证据链。**默认在当前树上构建并跑两批新的**，不要把批次 42 的旧目录直接当 A6 的一半。

### 3.2 安装代际（`install_generation_changed`）

- `installGenerationId = sha256(appSha + testSha + firstInstallTime + lastUpdateTime + versionCode + signaturesDigest)`（`dumpsys package <pkg>` 取值）。
- 两批必须完全相同。批次之间**不得重装**（`adb install -r` 会改 `lastUpdateTime`），哪怕字节相同。
- 若预注册明确允许"重装但字节相同"，必须把 `allowReinstall=true` 写进 `a6-plan.txt`，并在报告里标 `reinstall_between_batches`；默认不允许。
- **消灭的失败**：用重装清 dexopt/页缓存，把第二批变成"新装冷启动"而不是同一安装状态的第二次冷启动。

### 3.3 设备代际（`device_generation_changed`）

- `deviceGenerationId = sha256(serial + ro.build.fingerprint + ro.build.version.sdk + ro.build.id + ro.build.version.incremental + ro.product.model + ro.product.device + ro.product.cpu.abilist + pageSize + avdName + emulatorInstanceId)`。
- 两批必须完全相同。`serial` 单独不够：两台同镜像模拟器可能同 fingerprint；`fingerprint` 单独也不够：同 serial 可能在两次之间换了模拟器实例。
- 模拟器实例：`adb emu avd name` + 宿主 `qemu-system-*` 进程 PID/StartTime；真机 `emulatorInstanceId=NA`。
- 两次批之间模拟器进程重启、AVD 重建、系统镜像升级、设备恢复出厂 → 设备代际变化 → A6 NOT EVALUABLE；必须在**同一实例**上重跑两批。
- **消灭的失败**：两批分别跑在两台"看起来一样"的模拟器上，被当成同一设备。

### 3.4 启动代际（`boot_id_repeated` / `boot_id_overlap` / `boot_count_*`）

- 每轮宿主 `cat /proc/sys/kernel/random/boot_id`：`bootIdBefore` 与 `bootIdAfter` 必须非空且相等；40 轮必须两两不同；`set(A) ∩ set(B) = ∅`。
- 每轮 app `Settings.Global.BOOT_COUNT`（`bootCount`）：非空、非 -1、与宿主 `settings get global boot_count` 相等；40 个值两两不同；按执行顺序**严格递增**（允许间隔，不允许回退）。
- `bootCount(B.min) > bootCount(A.max)`；若 `bootCount` 回退 → `boot_count_reset`（恢复出厂/被改写）→ 设备代际变化。
- **`boot_id` 的语义有一手依据**：Linux 内核注释 `boot_id - a UUID representing the current boot`，proc 项 `mode = 0444`（`gh api` 实读 `torvalds/linux/drivers/char/random.c:1587,1690-1692`）；`man 4 random` 写 `boot_id ... was generated once`（`https://man7.org/linux/man-pages/man4/random.4.html`）。两者一致，采纳。app 侧 `BOOT_COUNT` 的 AOSP 原文是 `Boot count since the device starts running API level 24`、`@Readable`、常量 `"boot_count"`（`gh api` 实读 `aosp-mirror/platform_frameworks_base/core/java/android/provider/Settings.java:17763-17769`）。
- **不是主口径的"冷"**：`force-stop`（同 boot、同页缓存）、framework-only 重启（`adb reboot userspace` / `stop && start`，若未换内核 `boot_id`）、`am freeze/unfreeze`（解冻热进程）、模拟器快照/quick boot（可能复用 `boot_id`）——全部由 boot_id 门出局。
- **消灭的失败**：F10 的"20 轮同 bootCount 仍 PASS"；`force-stop` 20 次冒充 20 次冷启动；快照恢复冒充 reboot。

### 3.5 进程代际（`worker_hot` / `process_bit_drift` / `generation_missing`）

- 每轮测量前 `pidof <pkg>:visual_js` 必须为空；`pidWorker` 非空 → 该轮 INVALID（现有门）。
- 每轮测量前 `pidof <pkg>`（app 进程）记"存在/不存在"位；40 轮的位必须一致（全存在或全不存在）。若部分轮存在、部分不存在 → `condition_drift`（除非预注册了统一归一化，例如 boot 后统一 `am force-stop` 一次并记录）。
- 每轮 `KD76_SAMPLE` 必须带非空 `generation`；app 侧的 generation 过滤正例（传 `generation+1` 必须返回 null）由用例自身断言（`VisualJsConnectStageCalibrationInstrumentedTest.kt:500-510`）；断言失败 → 该轮 `<failure>` → G1 红。
- 每轮 logcat 至少要有一条 `visual_js warm-up finished`（`VisualJsService.kt:153`）；0 条 → `warmup_witness_missing`（该轮 INVALID）；>1 条 → `worker_restarted`（G0 的"无重建"被破坏，该轮 INVALID）。`Start proc .*:visual_js` 的 AMS 行作为辅助，必须出现在本轮 logcat（脚本轮前 `logcat -c`）。
- **`am instrument` 前后各读一次 `pidof`**：现在只在轮前读一次；建议在 `logcat -c` 之后再读一次 `pidof :visual_js`，消灭"检查后、测量前"的竞态。
- **消灭的失败**：worker 已在后台存活（热启动冒充冷启动）；worker 在本轮中途重启（时间戳/连接账不可比）；app 进程存在位跨批漂移。

### 3.6 证据代际（`run_id_reused` / `evidence_reused` / `raw_output_missing`）

- 每批生成 `runId`（随机 nonce，写入 manifest 和每条 `KD76_ENV`）；两批 `runId` 必须不同。
- 两批之间同号的 20 对文件不能全部逐字节相同；至少一对同号文件哈希不同。若 20 对全同 → `evidence_reused`（复制证据）。
- 每份 `round-NN.xml` 与 `round-NN.am.txt` 的 sha256 写入 manifest 的哈希链；composer 重算。哈希链只能防"无意改坏/局部改"，防不了"全量重造"——见 §7 的伪造阶梯。
- 每轮必须存在非空 `round-NN.am.txt`；XML 的 `<system-out>` 必须含 `--- am instrument output ---` 与 `OK (1 test)`；缺 → `raw_output_missing`（该轮 INVALID）。这一条消灭本轮探针里的"最小手写 XML 直接 PASS"。
- run 目录必须有 `manifest.sha256`（对 manifest 正文的哈希）；该值要抄进 run 目录外的批次记录/外部日志。只在同目录内自洽不算外部锚。
- **消灭的失败**：把 A 批复制成 B 批；只留绿轮、删失败轮；手写 XML 绕过 `am`。

### 3.7 时间分离（`time_overlap` / `separation_too_short` / `clock_anomaly`）

- **结构（硬）**：
  - `A.finishedUtc < B.startedUtc`；
  - 把 40 个轮次窗口按 `roundStartedUtc/roundFinishedUtc` 排序，任意两轮不重叠；
  - A 批最后一轮的 `roundFinishedUtc <` B 批第一轮的 `roundStartedUtc`。
- **间隔（策略，预注册）**：
  - `a6-plan.txt` 在 A 批开跑前写死 `minSeparationMinutes`；工具硬下限 10 min，建议 30 min；`observedGap = B.startedUtc - A.finishedUtc` 必须 ≥ 声明值。
  - 声明值 < 30 时报告 `separation_below_recommended`（不是判红，但必须在记录里显式披露）；声明值 < 10 → 直接拒绝。
  - 30 min 的依据是**本项目设计裁定**：真实一个 20 轮批约 19m56s（批次 42 manifest `:15,26`），30 min 大于一个完整批，能让宿主/模拟器的瞬态（构建、热、页缓存）换一个窗口；这不是外部统计定理，不写成"30 min 才独立"。
- **时钟（`clock_anomaly`）**：宿主墙钟可能回拨；用 `bootCount` 严格递增做交叉。若 `startedUtc` 顺序与 `bootCount` 顺序矛盾，或任一轮 `roundFinishedUtc < roundStartedUtc` → NOT EVALUABLE。
- **消灭的失败**：两批并行/交错跑；把一次长跑切成两段冒充两批；背靠背跑（同一瞬态窗口）却声称"两次独立"。

### 3.8 条件一致性（`condition_drift`）

- 两批必须同 `mode=reboot`、同 `settleSeconds=0`、同 `rounds=20`、同 `firstRound=1`、同 `class/method/component`、同 `gateMillis=5000`、同 `estimator=nearest-rank`；manifest 字段逐字相等。
- `S-warmup` 中位数比值 > 2× → `condition_drift`（沿用仓库既有先例 `VisualJsConnectStageCalibrationInstrumentedTest.kt:731-743`）。
- 宿主/设备负载：每轮 `/proc/loadavg` 的 `la1/deviceNproc`，两批中位数比值 > 2× → `condition_drift`。**不设绝对低负载门**：`settle=0` 的 boot storm 是预注册条件的一部分（R3 §2.5）。
- 屏幕：每轮 app 侧 `PowerManager.isInteractive` 必须为真；宿主侧 `dumpsys power` 的 `mWakefulness=Awake` / `Display Power: state=ON` 必须为真；否则该轮 INVALID（`uptimeMillis` 在 deep sleep 暂停会让段值偏小）。
- 模拟器 `Apps frozen` 数量、`use_freezer` 记录；不要求关闭 freezer（关闭会改变条件，需单独预注册）。
- 温度/电量：模拟器上只记录（thermal 假）；真机上温度 > 40 °C 或电量 < 20% → `condition_drift`（建议值，真机 runbook 预注册）。
- **消灭的失败**：两批一批在构建风暴、一批在空载，双双 PASS 却被当成"同条件两次"；屏幕熄灭导致段值偏小。

## 4. 执行形状（两批 20 轮的宿主脚本）

### 4.1 预注册文件 `a6-plan.txt`（在 A 批开跑前写死）

```
a6PlanVersion=1
planId=<uuid 或 2026-11-05T..Z-<nonce>>
writtenUtc=<A 批开始之前>
batchIds=A,B
requiredBatches=2
roundsPerBatch=20
estimator=nearest-rank
gateMillis=5000
mode=reboot
settleSeconds=0
minSeparationMinutes=30
maxReplacementBatches=1
expectedAppApkSha256=<64 hex>
expectedTestApkSha256=<64 hex>
expectedDeviceGenerationId=<64 hex>
expectedInstallGenerationId=<64 hex>
allowReinstall=false
```

- 写完后立刻算 `sha256sum a6-plan.txt`，写入两份 manifest 的 `a6PlanSha256`，并把该哈希抄进本批记录（run 目录外）。
- **消灭的失败**：跑完看结果再改 `minSeparationMinutes`/`maxReplacementBatches`/门；事后选口径。

### 4.2 批次 A

1. 构建并安装一次 app/test APK；记录构建产物 sha、`installed_apk_identity`、`dumpsys package` 的 firstInstallTime/lastUpdateTime/signatures、设备代际字段、AVD/实例。
2. 写 `a6-plan.txt` 并哈希。
3. 跑 20 轮：
   ```
   tools/ci/run_kd76_rounds.sh --serial <serial> --mode reboot --rounds 20 \
     --first-round 1 --batch-id A --run-id <nonce-A> \
     --out build/kd76-runs/a6/batchA \
     --apk <app.apk> --test-apk <test.apk>
   ```
   （`--batch-id`/`--run-id` 是本文建议的新参数，当前脚本没有；实现归 WS2 项 11。）
4. 每轮：reboot → `wait_for_boot` → 唤醒/屏幕 Awake → 读 `boot_id`/`boot_count`/`pidof`/`pidof :visual_js`/loadavg/freezer → `logcat -c` → 再读一次 `pidof :visual_js` → `am instrument -w -e class ...#readRoundFromInstrumentationArg -e smb.kd76.round N` → 读 `boot_id`/pid/loadavg → 写 `round-NN.am.txt` + `round-NN.xml`（含 `KD76_ENV`、`KD76_*`、am 原文、`--- am instrument output ---`）。
5. 批末写 `manifest.txt`（含 `runId`、`batchId`、`a6PlanSha256`、`installedAppSha256`、`installedTestSha256`、`deviceGenerationId`、`installGenerationId`、`startedUtc/finishedUtc`、`failedRounds`、`roundsRequested`、`bootIds`、逐文件哈希），再写 `manifest.sha256`。

### 4.3 批次 B

1. 等 ≥ `minSeparationMinutes`（建议 30 min）；确认模拟器实例未重启、设备代际未变、安装未变。
2. **不重装**（不传 `--apk`/`--test-apk`，或传同一文件但先证明 `lastUpdateTime` 不变）；先复核已安装 sha == A 批。
3. 跑 20 轮，`--batch-id B --run-id <nonce-B> --out build/kd76-runs/a6/batchB`。
4. 批末同样写 manifest + 哈希链。

> 复用历史批（例如批次 42 的 `ws3-batch42-20`）原则上允许，但必须通过 I0–I10；历史批缺 `runId`/`installGenerationId`/逐轮墙钟，默认不满足证据链。默认跑两批新的。

### 4.4 判词

```
python -I tools/ci/summarize_kd76.py build/kd76-runs/a6/batchA   # 每批独立
python -I tools/ci/summarize_kd76.py build/kd76-runs/a6/batchB
python -I tools/ci/kd76_a6_verify.py \
  --plan build/kd76-runs/a6/a6-plan.txt \
  --batch-a build/kd76-runs/a6/batchA \
  --batch-b build/kd76-runs/a6/batchB
```

- 前两条是**每批事实**，必须分开保留；第三条只做合取与独立性检查，不重算合并 p95。
- `kd76_a6_verify.py` 当前不存在；设计见 §8，实现归 WS2 项 11–17。

### 4.5 成本

- 真实 20 轮 ≈ 20 min（批次 42：19m56s）。两批 40 轮 ≈ 40 min，加 30 min 间隔 ≈ 70 min；共享模拟器上有他线构建时更长。
- 每一轮都 reboot，40 次 reboot；这是主口径的成本，不能用 force-stop/热启动压缩。

## 5. 判词规则

### 5.1 批级判词（沿用现有工具，不改）

对每批 X ∈ {A, B} 独立执行 `summarize_kd76.aggregate`：

| 批级判词 | 条件 | 退出码 |
|---|---|---|
| **PASS** | n=20、G1 绿（无 FAIL/INVALID/XML failure、无缺轮/重复/混 sha/混指纹/非 reboot/热 worker/boot 证明缺陷）、`M.p95 ≤ 5000` | 0 |
| **FAIL** | n=20、G1 绿、`M.p95 > 5000`（含 5001） | 1 |
| **NOT_EVALUABLE** | n<20 / G1 红 / 快照不一致 / 输入不完整 / boot 证明缺失或重复 / mode 非 reboot / 热 worker | 2 |

注意：**单轮 `status=FAIL` 走 G1 红 → 批级 NOT_EVALUABLE，不是批级 FAIL**。这是现有工具的口径（`summarize_kd76.py:491-503,537`）。但"NOT_EVALUABLE"只表示"出不了 p95"，**不表示失败没发生**；若失败轮归因产品，台账必须另记真红，不得当成环境噪声洗掉。

### 5.2 跨批独立性检查（新增）

| # | 检查 | 通过条件 | 理由码 |
|---|---|---|---|
| I0 | 预注册 | `a6-plan.txt` 存在、哈希与两份 manifest 的 `a6PlanSha256` 一致、`requiredBatches=2`、`roundsPerBatch=20`、`gateMillis=5000`、`estimator=nearest-rank`、`minSeparationMinutes>=10`、`maxReplacementBatches<=1` | `plan_missing` / `plan_mismatch` |
| I1 | 构建 | `installedAppSha256` A==B==plan；`installedTestSha256` A==B==plan；与构建产物 sha 一致 | `build_mismatch` / `installed_sha_mismatch` |
| I2 | 设备 | `deviceGenerationId` A==B==plan | `device_generation_changed` |
| I3 | 安装 | `installGenerationId` A==B==plan；`firstInstallTime`/`lastUpdateTime`/signatures 相同 | `install_generation_changed` |
| I4 | 协议 | `mode=reboot`、`settleSeconds=0`、`rounds=20`、`firstRound=1`、`class`/`method`/`component`/`gateMillis`/`estimator` 逐字相同 | `protocol_mismatch` |
| I5 | 时间 | A.finished < B.started；40 个轮次窗口无重叠；`observedGap >= minSeparationMinutes`；时钟顺序与 bootCount 顺序不矛盾 | `time_overlap` / `separation_too_short` / `clock_anomaly` |
| I6 | 启动 | 40 个 `boot_id` 两两不同、A∩B=∅、每轮 before==after；40 个 `bootCount` 非空、与宿主一致、严格递增；`bootCount(B.min) > bootCount(A.max)` | `boot_id_repeated` / `boot_id_overlap` / `boot_count_mismatch` / `boot_count_not_increasing` / `boot_count_reset` |
| I7 | 进程 | 40 轮 `pidWorker` 全空；`pidTarget` 位 40 轮一致；每轮 `generation` 非空；每轮恰好 1 条 `warm-up finished`、无 worker 重建 | `worker_hot` / `process_bit_drift` / `generation_missing` / `worker_restarted` / `warmup_witness_missing` |
| I8 | 条件 | `S-warmup` 中位数比 ≤2×；`la1/nproc` 中位数比 ≤2×；40 轮屏幕 Awake；模拟器实例未重启；freezer 数记录；温度/电量在预注册范围（真机） | `condition_drift` |
| I9 | 证据 | 每批恰好 20 份 XML + 20 份非空 `.am.txt`；两批 `runId` 不同；两批同号 20 对文件不全同；哈希链重算通过；XML 含 am 原文与 `OK (1 test)` | `evidence_reused` / `run_id_reused` / `raw_output_missing` / `hash_chain_broken` |
| I10 | 不重试 | 每批 `roundsRequested=20`、`failedRounds=0`、无 21..40 越界轮、manifest 的 `replacementCount` ≤ `maxReplacementBatches`、所有作废批保留 | `optional_stopping` / `retry_budget_exceeded` |

### 5.3 A6 合成判词（穷举）

先收集所有理由，不短路；再按顺序判定：

| batch A | batch B | I0–I10 | A6 判词 | 含义 |
|---|---|---|---|---|
| PASS | PASS | 全绿 | **A6: CONFIRMED** | 同一构建、两次独立完整 n=20，各自过 G1/G2；可作为 KD-76 的 A6 关闭证据（仍不等于 C4/真机） |
| PASS | FAIL | 全绿 | **A6: REFUTED** | 第二次完整判定 p95>5000，复现失败；产品红 |
| FAIL | PASS | 全绿 | **A6: REFUTED** | 第一次完整判定 p95>5000；不能拿第二次绿覆盖 |
| FAIL | FAIL | 全绿 | **A6: REFUTED** | 两次都红；稳定复现 |
| PASS | NOT_EVALUABLE | 任意 | **A6: NOT EVALUABLE** | 第二次出不了判词；不能确认 |
| NOT_EVALUABLE | PASS | 任意 | **A6: NOT EVALUABLE** | 第一次出不了判词；不能确认 |
| FAIL | NOT_EVALUABLE | 任意 | **A6: NOT EVALUABLE** | 第一次红、第二次出不了判词；不能确认 |
| NOT_EVALUABLE | FAIL | 任意 | **A6: NOT EVALUABLE** | 第二次红、第一次出不了判词；不能确认 |
| NOT_EVALUABLE | NOT_EVALUABLE | 任意 | **A6: NOT EVALUABLE** | 两次都出不了判词 |
| 任意 | 任意 | 任一红 | **A6: NOT EVALUABLE** | 测量设计/条件缺陷；先修再跑 |
| PASS | PASS | I0–I7/I9/I10 绿但 I8 `condition_drift` | **A6: NOT EVALUABLE** | 两批条件不可比；不是"两次独立" |

补充规则：

```python
# 伪代码：先收集，不短路；判词只用 per-batch Report.verdict，不重算合并 p95
reasons = check_i0_i10(plan, manifest_a, manifest_b, rows_a, rows_b)
if reasons:
    return NOT_EVALUABLE(reasons)
if report_a.verdict == "NOT_EVALUABLE" or report_b.verdict == "NOT_EVALUABLE":
    return NOT_EVALUABLE(["batch_not_evaluable", ...])
if report_a.verdict == "FAIL" or report_b.verdict == "FAIL":
    return REFUTED(["p95_over_gate", ...])
return CONFIRMED([])
```

1. **REFUTED 只用于"两批都可出 p95、且至少一批 p95>5000"**。单轮 FAIL/INVALID/缺轮 → 批级 NOT_EVALUABLE → A6 NOT_EVALUABLE；若失败轮归因产品，另记 `product_red`，不因 A6 NOT_EVALUABLE 而消失。
2. **A6 CONFIRMED 不产生"合并 p95"**。判词行只写两批各自的 n/p95/max，不写 n=40、不写 combined p95。
3. **A6 CONFIRMED 不覆盖 C4/29.5 s/arm64/真机**；这些仍是独立条件（§9）。
4. **替换批**：某批因测量缺陷（reboot 超时、boot_id 不可读、屏幕熄灭、worker 热）判 NOT_EVALUABLE，可在预注册的 `maxReplacementBatches` 内重跑该批；替换批必须在看到结果前声明，所有作废批保留在 `attempt-<n>` 目录。产品 FAIL 不得重跑洗绿。
5. **可选停止**：不得"跑到两批绿为止"。`maxReplacementBatches<=1` + 全部 attempt 保留 + 独立见证，是唯一可审计的约束；工具本身无法证明没有多跑。

### 5.4 判词行模板（text）

```
A6: CONFIRMED
  batchA: n=20/20, G1 green, M.p95=1889 ms <= 5000 ms, max=2089 ms, runId=..., app=35e1...
  batchB: n=20/20, G1 green, M.p95=1969 ms <= 5000 ms, max=2218 ms, runId=..., app=35e1...
  independence: build same; deviceGeneration same; installGeneration same;
```

规则：`A6: NOT EVALUABLE` 的文本**不得出现 `A6: CONFIRMED`**；批级 `PASS` 只能带 `batchX:` 前缀出现，且必须紧邻 A6 判词行，避免被读成 A6 通过。

## 6. 合并规则：为什么禁相加

### 6.1 禁止清单

| 禁止操作 | 为什么 | 本轮探针/依据 |
|---|---|---|
| 报 `n=40` | A6 不是 40 个样本的一次门；两批各自预注册 n=20 | 计划 `:40` "不合并 n"；`summarize_kd76.py:60` |
| 把两批 XML 放一个目录算 p95 | 轮号重复直接 NOT EVALUABLE；即使改号 21..40 也被 `unexpected round ids` 拒绝 | 探针 A/C：`exit=2` |
| 平均两批 p95 | 分位数不可加；平均分位数没有统计意义 | Prometheus 官方："you cannot aggregate quantiles"；探针 avg=418 |
| 相加两批 p95 / 段值 | 分位数不是可加量；段值的和是另一个估计量 | 同上；R2 §3.4 |
| 用 `max(p95A,p95B)` 当"合并 p95" | 它数值上等价于"两批都 ≤ 门"的合取，但**不是**一个合并估计量；写成"合并 p95"会误导 | 本协议 §5.3；可作"较差批"描述 |
| 把 n=40 的 p95 当门 | n=40 的 p95 是第 38/40 个，容忍 2 个最大值；n=20 只容忍 1 个，合并静默放宽 | 探针：n=40 p95=517；R3 §3.5（`docs/research/2026-11-04-kd76-20-rounds.md:191-195`） |
| 用线性插值 p95 | 与 nearest-rank 是两套估计量 | `summarize_kd76.py:332-337`；R2 §2.1 |
| 只报一个 p95 不给两批向量 | 无法审计"哪批红/哪批绿" | R3 §3.1（`docs/research/2026-11-04-kd76-20-rounds.md:151-152`） |

### 6.2 允许的报告

- 两批各自 `n/min/p50/p90/p95/max/sorted`，并列。
- 每批 `gateMargin = 5000 - p95`（毫秒）；负值即 G2 FAIL，不取绝对值掩盖。
- 两批 `max(p95A,p95B)` 作为"较差批的 p95"（描述，不是合并估计量）。
- `p95Ratio = max/min` 作为复现离散度（描述；>2× 标 `high_replication_spread`，不是新门）。若出现 >2×，记录必须显式披露；主会话可据此要求额外批次，但**工具不得自行发明新门**。
- 两批的 boot_id 集合、bootCount 范围、时间窗口、设备/安装/构建代际并列。
- 所有原始 M 向量（20+20）保留，供独立复算。

### 6.3 本轮探针的合并反例（可复核）

```
D1 batchA only: exit=0  G2: PASS (M.p95=318 ms)
D2 batchB only: exit=0  G2: PASS (M.p95=518 ms)
A  two dirs both 1..20: exit=2  duplicate round evidence [1..20]
C  batchA 1..20 + batchC 21..40: exit=2  unexpected round ids [21..40]
E  p95(n=20 A)=318  p95(n=20 B)=518  p95(merged n=40)=517  avg=418.0
```

三个"合并"数字（517 / 418 / 518）互不相等；这不是数值误差，而是**估计量换了**。A6 判词只能用 318 和 518 两个独立门。

## 7. 可伪造点与反制

> 强度分三档：**结构性**（工具/签名直接拒绝，改不了）> **证据性**（需要交叉证据/哈希链，能防局部改，防不了全量重造）> **流程性**（只能靠独立见证/外部锚）。没有一个本地检查是 tamper-proof；本表如实标注。

### 7.1 伪造点总表

| # | 伪造/漂移手法 | 当前工具能否抓住（本轮实测/实读） | 协议反制 | 强度 |

| F1 | 把 A 批 20 份 XML 原样复制成 B 批 | **单独跑两批都 PASS**（探针：最小 XML 夹具的逐字节副本，A/B 各 `exit=0`，20 份哈希全同）；两批一起传反而 `duplicate round evidence` `exit=2` | `runId` 不同 + 20 份哈希不全同 + boot_id 交集为空 + 时间窗口不重叠 | 结构性（若复制者不改 runId/哈希）→ 证据性（可重造） |

### 7.2 伪造阶梯（诚实边界）

| 级别 | 手法 | 本地工具能否抓住 | 需要什么 |
|---|---|---|---|
| L0 事故 | 脚本 bug 导致缺字段/轮号错 | 能（结构性） | 现有门 + 新增 plan/代际检查 |
| L1 疏忽 | 忘传 `--apk`、mode 错、settle 非 0 | 能（manifest 比对） | 新增 I4 |
| L2 局部改 | 改一份 XML 的 boot_id/时间/段值 | 部分能（三源 + 哈希链） | 新增 I6/I9 |
| L3 全量重造 | 重新生成 20 份 XML + manifest + 哈希链 | **不能** | 外部时间戳/append-only 日志/独立见证 |
| L4 宿主/ADB 伪造 | 假 adb、假 /proc、假设备 | **不能** | 受信环境 + 硬件/外部见证 |

结论：A6 的"可判定"必须建立在 **L0–L2 可被工具抓住、L3–L4 由流程与独立见证兜底** 的分层上；不能声称"脚本能证明没造假"。

## 9. 未验证、边界与外部阻塞

### 9.1 本轮未执行（UNVERIFIED）

- **两次 20 轮实跑未发生**：零 reboot、零 `am instrument`；本协议的所有 A6 判词都是规则，不是实测。
- **跨批 boot_id 不交、时间顺序、设备代际一致未在同一构建的两批上验证**：批次 42 的两批只验证了"构建代际不同 → 不是 A6"。
- **`kd76_a6_verify.py` 不存在**：设计未落码；`--batch-id`/`--run-id`/per-round 墙钟/哈希链均未实现。
- **`generation` 非空、`warm-up finished` 计数、第二次 `pidof`**：未在设备上验证。
- **`minSeparationMinutes=30`**：本项目设计裁定，无外部统计依据；未做主会话确认。
- **真实设备/arm64/低内存/温度**：全部未验证；当前只有 x86_64/API 34 模拟器口径（批次 42）。
- **A6 on emulator 的用户代表性**：Android Macrobenchmark 官方明确"discourage running the benchmarks on an emulator, as they don't produce performance numbers representative of the end-user experience"（本轮抓取 `https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview`）。A6 在模拟器上只能作为回归/复现性证据，不能写成用户可感性能。
