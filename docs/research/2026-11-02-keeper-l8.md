## 0. 一句话结论与本次新增事实

**上游 `slackhq/Keeper` 0.16.1 在 AGP 9.3 上结构性不可用**（issue #152 仍 OPEN：AGP 9.0.0 默认 `android.newDsl=true` 下 apply 即崩 `Extension of type 'AppExtension' does not exist`）；**唯一可行对象是活跃 fork `usefulness/keeper` v0.19.0**，且它恰好在 **AGP 9.3.0 + Gradle 9.6.1** 上构建与测试（v0.19.0 tag 的 `libs.versions.toml` = `google-agp = 9.3.0`、wrapper = `gradle-9.6.1`；Maven Central 模块元数据 `createdBy.gradle.version = 9.6.1`；tag commit 的 CI `Build Project` 全绿）。**R-04 仍维持阻塞**：本会话未跑 Gradle，未产出 K2/K6 证据；是否采纳 Keeper 归主会话裁定（§9）。

本会话相对 P38 的**新增事实/勘误**（均有实跑证据）：

1. **AGP 9.3 官方兼容面**：最低/默认 Gradle **9.5.0**、JDK **17**、最高 API **37**（官方 release notes 实取）；本仓 Gradle **9.6.1** 高于最低线，但不是官方“默认”版本——兼容证据来自 fork 的精确构建/CI，而非 Google 的逐版声明。
2. **`settings.gradle.kts` 仍不需要编辑**：`pluginManagement.repositories` 已含 `google()`/`mavenCentral()`/`gradlePluginPortal()`（`settings.gradle.kts:2-5`），插件 marker 在 Maven Central 实取存在。P38 的“最小接入不编辑 settings”结论成立。
3. **但 Keeper 默认的 `automaticR8RepoManagement=true` 会被本仓 `FAIL_ON_PROJECT_REPOS` 直接判死**：Keeper 在该模式下执行 `with(project.repositories) { maven { ... } }`（`InferAndroidTestKeepRules.kt:175-188`），而本仓 `settings.gradle.kts:10` 设为 `RepositoriesMode.FAIL_ON_PROJECT_REPOS`。接入必须显式 `automaticR8RepoManagement.set(false)`；这是 P38 未覆盖的硬约束。
4. **`automaticR8RepoManagement=false` 后 R8 9.1.31 从现有 `google()` 解析是“可行但待 K2 证实”**：Google Maven 的 `com.android.tools:r8:9.1.31` POM/jar 均 200（jar 18,963,189 B，sha256 `3b4de305…`），`TraceReferences --version` 与一次不完整输入的 TraceReferences 运行均能启动（与 56,139,716 B 的 raw fat jar 同版本、同诊断形态、同 exit code）；但**完整 fat app/test jar 上的真实运行未跑**（§8-U3）。若失败，回退到“init script 在 settings 级加 raw 仓库”或“vendored raw jar”，仍不编辑 `settings.gradle.kts`。
5. **Keeper 会把 `testVariant.proguardFiles` 原样喂给主包 R8**（`KeeperPlugin.kt:287-293`），而本仓该文件含 `-keep class com.tingyun.smartmistakebook.** { <init>(...); @Test ... }`（`app/r04-test-keep.pro:22-29`）。启用 Keeper 后，R-04 实验变体的**主包 app 类会被整体保名**，K4“release mapping 有真实改名”仍可能靠库类通过，但实验保真度下降。补丁草案给出“接受（A）/收窄（B）”两案与判据（§4.4）。
6. **mapping 三值预检的精确字面量在 AGP 9.3.0 上不是稳定门**：AGP 9.3.3 才修复 Issue #554586985“R8 build non-determinism: identical input produces different dex/mapping”与 #522844908“Duplicate mapping with R8 9.1”（官方 release notes 实取）；本仓钉 9.3.0。Keeper 的 L8 规则合并又会改变主 L8 的短名分配。因此 **①/② 的 `j$.util.g` 字面量只能作快照值，不能作语义门**；L8 合并后的验证应以“主 dex 有 `SynchronizedMap` 的类定义（原名或映射目标）+ 测试 dex 的 j$ 类定义数 = 0”为准，主 mapping 的 L8 段作为诊断（§5.3）。这属于**门的重新锚定**，会改变既有门语义，须主会话裁定；不得静默放宽。

### 3.5 残余风险（都真，需登记）

1. **私有 API 依赖**：Keeper docs 自述 “uses private APIs from AGP and could break between releases”（P38 §3 已引）；fork 继承同一风险。v0.19.0 精确面对 AGP 9.3.0，但 AGP 9.3.x 的补丁版（9.3.1/9.3.2/9.3.3）未逐一验证；本仓钉 9.3.0，风险面可控。
2. **维护面薄**：0 star、单维护者、默认分支 `master` 比 0.19.0 超前（AGP 9.5.0 / Gradle 9.8.2），但**没有 0.20 发布**；必须钉 0.19.0，不得追 master/snapshot。
3. **插件 POM 的 `kotlin-stdlib 2.4.0`**：本仓 `kotlin = 2.3.21`。插件在 buildscript classpath，不在 app 运行时图；Gradle 9.6.1 的 embedded Kotlin 能加载（fork CI 同 Gradle 版本），但本仓 KGP 2.3.21 与 stdlib 2.4.0 的 buildscript 解析未实测（§8-U7）。若 KGP 报元数据/API 错，优先用 `pluginManagement.resolutionStrategy` 或 buildscript 约束回 2.3.21——那会触 `settings.gradle.kts` 热区，须先裁定。
4. **R8 构件来源**：默认 9.1.31 需要 `com.android.tools:r8`；`automaticR8RepoManagement=false` 时只能从现有 `google()` 取（§4.2/§4.3）。
5. **测试 keep 传播**：见 §4.4，属于实验保真度而非运行时阻断。

## 4. 接入补丁草案（只出草案；`settings.gradle.kts` 零编辑）

### 4.1 热区约束与结论

- `settings.gradle.kts` 是共享热区（计划 §2；批次 40 共享纪律）。本会话**不编辑**它；本草案也不要求编辑它。
- **插件解析**：`pluginManagement.repositories` 已含 `google()`、`mavenCentral()`、`gradlePluginPortal()`（`settings.gradle.kts:2-5`）；`io.github.usefulness.keeper` marker 在 Maven Central 实取存在（§3.1）。**无需 settings 编辑。**
- **R8 解析**：`dependencyResolutionManagement.repositories` 已含 `google()`（`settings.gradle.kts:12`）；`com.android.tools:r8:9.1.31` 在 Google Maven 实取 200（POM + jar）。**若 K2 证明该 thin jar 可跑完整 TraceReferences，则无需 settings 编辑。**
- **硬约束**：本仓 `repositoriesMode = FAIL_ON_PROJECT_REPOS`（`settings.gradle.kts:10`）；Keeper 默认 `automaticR8RepoManagement=true` 会走 `project.repositories`（`InferAndroidTestKeepRules.kt:180-187`），**必崩**。因此补丁必须 `automaticR8RepoManagement.set(false)`。
- **禁止**：为 Keeper 修改 `FAIL_ON_PROJECT_REPOS`、在 `settings.gradle.kts` 加 raw R8 仓库、或把 settings 解冻当“顺手改动”。若 thin jar 路线失败，按 §4.3 的回退走 init script / vendored jar，仍不编辑 settings。

### 4.3 `automaticR8RepoManagement=false` 后的 R8 解析：可行性与回退

本会话实测：

```bash
# Google Maven（现有 settings 的 google() 会命中）
curl -s -o /dev/null -w "%{http_code}\n" https://dl.google.com/android/maven2/com/android/tools/r8/9.1.31/r8-9.1.31.pom   # 200
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" https://dl.google.com/android/maven2/com/android/tools/r8/9.1.31/r8-9.1.31.jar
# 200 18963189
sha256sum r8-9.1.31.jar   # 3b4de3053885da105e39c15212261d22653d6d1b5eb92323dd04ae913cc8286f

# 启动探针
java -cp r8-google.jar com.android.tools.r8.tracereferences.TraceReferences --version
# tracereferences 9.1.31 (build 60751e845e0a27ed4dd4f3d50e53c9f196fa30bb …)
```

- Google Maven 的 jar 是 **18.96 MB 的 thin jar**（不含未 shade 的 `com/google/common` / `org/objectweb/asm` 类；`unzip -l | grep -c` = 0），而 `r8-releases/raw` 的 jar 是 **56.14 MB 的 fat jar**（包含这些类）。但 thin jar 能启动 `TraceReferences`，并在一次不完整输入（只有 `android.jar` + app classes jar）上与 raw jar 产生**相同的诊断形态与 exit code（1）**，没有 R8 运行期 `NoClassDefFoundError`。这说明 thin jar 对 TraceReferences 路径**很可能**自足；**完整 fat app/test jar 上的真实运行未跑**（§8-U3）。
- **主路线**：`automaticR8RepoManagement=false` + 现有 `google()`，K2 实跑 `:app:inferStrictOfflineReleaseKeepRulesForKeeper` 验证。若该任务报 R8 运行期缺类/缺依赖，按下面回退。
- **回退 1（不编辑 settings；形态未实测）**：在 `tools/ci/` 放一个 init script，在 `settingsEvaluated` 阶段向 `dependencyResolutionManagement.repositories` 加 `https://storage.googleapis.com/r8-releases/raw`（仅 `com.android.tools:r8`），K2 命令加 `-I tools/ci/keeper-r8-repo.init.gradle.kts`。这仍然不改 `settings.gradle.kts`，但把“仓库来源”移到了命令行参数；CI 必须显式带上，否则构建不可复现——须主会话批准这种运维形态。
- **回退 2（不编辑 settings、不改命令行）**：vendored raw fat jar（56 MB）入仓或入构建缓存，`keeperR8(files("…/r8-9.1.31.jar"))`；需要 sha256 门与仓库体积评估。**不推荐**，仅作最后手段。
- **禁止**：把 raw 仓库写进 `settings.gradle.kts` 或去掉 `FAIL_ON_PROJECT_REPOS`——这是热区改动，须先解冻裁定。

### 4.4 `testProguardFiles` 传播：实验保真度问题（本会话新发现）

Keeper 的 `KeeperPlugin.kt:287-293` 会把 `testVariant.proguardFiles` 追加到**主包** R8 的 `configurationFiles`。本仓该文件是：

```proguard
# app/r04-test-keep.pro:22-29
-keep class com.tingyun.smartmistakebook.** {
    <init>(...);
    @org.junit.Test <methods>;
    @org.junit.Before <methods>;
    @org.junit.After <methods>;
    @org.junit.BeforeClass <methods>;
    @org.junit.AfterClass <methods>;
}
```

`-keep class com.tingyun.smartmistakebook.**` 是**广域保类/保名**规则。进入主包 R8 后，R-04 实验变体的 app 类会被整体保名，主 mapping 的 app 段退化为 identity；K4 “release mapping 有真实改名”仍可能靠库类通过，但“release 包真的把 app 类混淆了”这一实验前提被削弱。这是**代码级推断**（Keeper 源码 + 现有 keep 文件），K2 后可用 `app/build/outputs/mapping/strictOfflineRelease/configuration.txt` 是否出现 `r04-test-keep.pro` 段来证实（当前该文件只有注释提及，无规则；`grep -c '^-keep class com.tingyun'` = 0）。

两案（须主会话裁定，不擅自改）：

- **案 A（最小改动）**：保留 `r04-test-keep.pro` 原样，接受“R-04 实验变体 app 类不混淆”。优点：改动面最小，Keeper 的 j$ L8 修复仍被 K6 覆盖；缺点：实验保真度下降，K4 的“真实改名”只对库类成立。
- **案 B（推荐，收窄测试 keep）**：把规则 1 改为“只保真正含 `@Test` 的测试类”，既保留 instrumentation 按类名加载，又不把 app 类带进主包 R8：

```proguard
# 只匹配“有构造器 + 至少一个 @Test 方法”的类；app 主类没有 @Test，不会命中。
-keepclasseswithmembers class com.tingyun.smartmistakebook.** {
    <init>(...);
    @org.junit.Test <methods>;
}
# 生命周期方法按注解保（类未被上一条保留时自然无效果）。
-keepclassmembers class * {
    @org.junit.Before <methods>;
    @org.junit.After <methods>;
    @org.junit.BeforeClass <methods>;
    @org.junit.AfterClass <methods>;
}
```

案 B 的验证：K5b（测试类名在 androidTest dex 未改名，`grep -a -c "VisualJsIsolationInstrumentedTest"` ≥1）必须仍过；K6 两例 `OK (2 tests)` 必须仍绿；主包 `configuration.txt` 中不应再出现广域 `-keep class com.tingyun.smartmistakebook.**`。案 B 不是放宽门——它**加强**了主包混淆面，但改变了测试 keep 语义，属于须裁定的变更。

### 5.3 L8 规则合并后的 mapping 三值预检（本文件核心交付）

#### 5.3.1 旧口径为什么不能原样复用

- **① 的精确字面量**：Keeper 把 test L8 的 keep rules 并入 app L8（`KeeperPlugin.kt:173-177`）。app L8 的保留集变化会改变 `j$` 短名分配；`SynchronizedMap` 可能仍映射到 `j$.util.g`，也可能换成别的短名，甚至被 keep 成原名。再加上本仓钉 **AGP 9.3.0**，而 AGP 9.3.3 才修复 Issue #554586985 “R8 build non-determinism: identical input produces different dex/mapping”（官方 release notes 实取），精确短名本来就不是跨构建稳定的。**① 的字面量只能作快照值，不能作语义门。**
- **② 的 mapping 代理**：Keeper 只清 `desugarLibDex` 输出（`KeeperPlugin.kt:206-213`），**没有清 L8 mapping**；AGP 9.3 当前产物在**主/测两份 mapping 都各有 1 个 `# L8 Desugaring Mapping` 段**（§1.2 实测）。因此测试 L8 任务仍会产出 mapping，并很可能仍被追加进测试 mapping → **旧 ② 的 `grep` 预计仍为 1**，即使测试 APK 已经不再携带 L8 dex。把旧 ② 继续当硬门，会把一个运行时已修好的构建误判为红。该结论是源码 + 产物结构的**推断**，K2 必须实测（§8-U2）。
- **② 的真正语义**是“测试 APK 不占用主包改名产物名”。Keeper 后应直接检查**测试 APK 的 dex 里有没有 `Lj$/…` 类定义**，而不是查 mapping 代理。直接检查更强（运行时载体），不是放宽。

#### 5.3.2 建议的 v2 口径（须主会话裁定）

| 预检 | v1（批次 36 原文） | v2（建议） | Keeper 后期望 | 依据 |
|---|---|---|---|---|
| ① | 主 mapping 含 `DesugarCollections$SynchronizedMap -> j$.util.g` ≥1 | **主 dex 有 `DesugarCollections$SynchronizedMap` 的类定义（原名或映射目标）**；主 mapping 的 `# L8 Desugaring Mapping` 段与短名作诊断（存在则记录，不强制 `=1`/`g`） | 结构过 | 合并 keep 可能把该类 keep 成原名；AGP 9.3.0 短名非确定（#554586985） |
| ② | 测试 mapping ` -> j$.util.g:` = 0 | **测试 APK 的 `classes*.dex` 中 `Class descriptor : 'Lj$/…'` 定义数 = 0**；旧 mapping grep 降为诊断值（记录，不作硬门） | 0 | 直接检查运行时载体；Keeper 清测试 L8 dex |
| ③ | 主包 dex 按名含 `androidx/tracing/Trace` ≥1 | 不变（仍为硬门） | ≥1 | `app/proguard-rules.pro:35-39` keep 未动；Keeper 不改 |
| ④（新增） | — | 主/测 dex 类描述符交集 = 0（尤其 `Lj$/util/g;`） | 0 | 碰撞的通用不变式；比单名检查更强 |
| ⑤（新增） | — | `app/build/intermediates/desugar_lib_dex/strictOfflineReleaseAndroidTest/**/*.dex` 无正尺寸文件 | 空 | Keeper `clearDir` 生效；防 up-to-date 残留 |

**首次启用 Keeper 的 up-to-date 陷阱**：Keeper 靠 `L8DexDesugarLibTask` 的 `doLast` 清空 `desugarLibDex`（`KeeperPlugin.kt:206-213`）。如果该任务在此前（未启用 Keeper 的构建）已经产出 dex 且输入未变，Gradle 可能判 UP-TO-DATE，`doLast` 不执行，旧 dex 会留在输出目录并被测试 APK 打包，导致 ⑤ 非空、K6 仍红。因此**首次 Keeper K2 前**必须显式清掉该中间产物或强制重跑，例如：

```bash
rm -rf app/build/intermediates/desugar_lib_dex/strictOfflineReleaseAndroidTest
# 或：./gradlew :app:l8DexDesugarLibStrictOfflineReleaseAndroidTest --rerun-tasks -Psmbk.testBuildType=release
```

之后每次 K2 用 ⑤ 复核；若 ⑤ 非空，按 §5.5 归因，不得直接上设备。

## 6. 回滚

### 6.1 单元回滚步骤

1. 还原三个构建文件：`gradle/libs.versions.toml`、根 `build.gradle.kts`、`app/build.gradle.kts`（或 revert 实施批 commit）。
2. `app/r04-test-keep.pro`、`app/proguard-rules.pro` **保留不删**（尤其 `-keep class androidx.tracing.Trace` 与 `-keep class j$.**`；它们是 R2 机制②确认有效的半边，且对 `.pro` 面无害）。若案 B 已改规则 1，回滚到案 A 的广域版本或按裁定保留收窄版——**不得**把 keep 文件回滚成“无规则”。
3. 锁：删除/忽略 Keeper 引入的锁状态；**不要手改锁**。KD-72 窗口未满足时，锁仍是未跟踪文件，回滚后按干净树 `lockAllDependencies --write-locks` 重生成（或保持未跟踪并登记）。
4. 清理 Keeper 中间产物，避免 build cache 复用：删除 `app/build/intermediates/keeper/` 与 `app/build/intermediates/desugar_lib_dex/strictOfflineReleaseAndroidTest/`（构建产物，非源码）。
5. 重跑 K2；若上过设备，按批次 35 步 5/步 6 恢复 debug 态（卸两 release 包 + 重建重装 debug 四包）。

### 6.3 触发条件与部分回滚

- **触发**：K2 失败且两轮修复不能归因到本批夹具/环境；K6 红且归因不是 A/B/C/D 常规面；Keeper 私有 API 在 AGP 9.3.0 上直接崩；锁窗口无法满足导致构建不可复现；configuration cache 不可用且无法归因本批。→ 回滚 + 按阻塞登记，R-04 回到批次 39 末状态（预检②结构性不可满足的机制证据仍有效，不因回滚失效）。
- **部分回滚**：把 `beforeVariants` 条件收窄到不再命中任何变体 = Keeper 等价 no-op（插件仍 apply，但不建推断/ L8 任务）；这只能作为“禁用而不摘除”的中间态，不是完整回滚——插件 classpath 与锁仍变。若要彻底恢复，按 §6.1 摘除插件。
- **禁止**：以回滚为由删除 `Trace` keep、放宽 K6 判据、引入 `-dontobfuscate`/`-dontshrink`/`-dontoptimize`、换 internal 变体、删例。
