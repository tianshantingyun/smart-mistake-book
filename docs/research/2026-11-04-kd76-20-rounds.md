## 0. 结论（pick）

1. **主口径不是"跑 20 次"，而是"20 个独立 boot 的单轮证据"**：每轮一次 `adb reboot` → 一次独立 `am instrument -e smb.kd76.round N` → 一份 `round-NN.xml`；20 个 `boot_id` 全不同、`boot_id` 前后不变、每轮 `:visual_js` 进程在测量前不存在。缺任一条即 NOT EVALUABLE。
2. **boot_id 走宿主通道，不走 app 的 `/proc`**：`/proc/sys/kernel/random/boot_id` 是 0444 的 `proc_random`，内核注释明确为 "a UUID representing the current boot"；宿主 `adb shell cat` 已实测可读（`12abf474-…`）。app 侧继续用 `Settings.Global.BOOT_COUNT`（API 24、`@Readable`、E-41-D04 实测 bootCount=2）做**交叉核对**，不要求 app 读 `/proc`。
3. **进程冻结的几种机制必须分开裁定**：Cached Apps Freezer 可以存在（reboot 后测量前无 `:visual_js`；绑定服务不被缓存；仅记录 `Apps frozen:` 数）；`am freeze` 是热进程解冻，不是冷启动，拒绝作主口径；模拟器快照/quick boot 可能复用 boot_id，门会判 NOT EVALUABLE（`tools/start-emulator.ps1:32` 已用 `-no-snapshot`）。
4. **force-stop 不是主口径**：它保留同一 boot（boot_id 不变）、保留 OS 页缓存，并可能命中被冻结的缓存进程；只能作非主口径 smoke。当前汇总脚本对此**没有门**——20 轮同一 bootCount 仍会打印 `G2: PASS`（§8 探针 D）。
5. **空 per-round sha/fingerprint/bootCount 是当前最危险的洞**：探针 B/C/I/J/N 证明，只要其余轮各自带齐身份字段，空 sha/空 fingerprint/缺 META/缺 ROUND/全缺 bootCount 的 20 轮仍会 `PASS`。处置必须是"该轮 INVALID、计入 20 个槽位、不得整轮静默剔除、不得补一轮凑 20"。
6. **两批 10+10 合并的最小障碍是轮次编号**：脚本只会写 `round-01..10`；两次各 10 轮会得到重复轮号，汇总判 `NOT EVALUABLE`（探针 G）。要么一次 `--rounds 20`，要么给脚本加 `--first-round 11`（探针 H 证明 1..10 + 11..20 可合并）。合并的是**原始样本**，不是两批 p95。
7. **n=20 的 nearest-rank p95 是第 19 个观测值**（`ceil(19)-1=18`，0 基），容忍恰好一个最大值；n=10 时 p95≡max。固定向量 `1..20` 复算 p95=19；加一个 9999 仍是 19。不得插值、不得换 p90、不得跨 n 比较。
8. **G1 与 G2 是合取**：任一轮 FAIL/INVALID/XML failure → G1 红 → **NOT EVALUABLE**，不出 p95；只有 20 个有效 SAMPLE、G1 绿，才轮到 G2（p95≤5 000 ms → PASS；>5 000 → FAIL）。`runner exit 1` 不是产品 FAIL，是测量失败 → NOT EVALUABLE。
9. **FAIL 是删失、INVALID 是测量系统缺陷**：FAIL 记 ≥ 预算（connect 15 000 ms / 宿主阶段 2 500 ms）并进 G1，不丢点、不缩尾、不重跑洗绿；INVALID 不给删失下界，整批作废、修 seam/夹具后重跑。
10. **两批是"抗单次偶然"的 closure 要求，不是 p95 的统计前提**：n=20 单批在分位数上与 10+10 等价；但 R2 A6 要求两批独立冷启动均 G1 绿。每批 n=10 的 p95 是 max，**不得**拿单批 p95 去卡 5 000 ms；门只施于合并后的 n=20。
11. **M 与 READY_TIMEOUT 的关系**：M=S-bind+S-warmup，S-bind 预算 15 000 ms、S-warmup 预算 10 000 ms；5 000 ms 门是 `READY_TIMEOUT/2` 的预注册产品余量，不是 M 的最坏值（25 000 ms）除以 2。**不改 10 s 阈值**；p95 红先归因到段，不靠放宽门或加沉降洗绿。
12. **判词单一事实源**：设备侧 `Kd76ReportVerdict.decide(...).verdictLine()`；跨轮由 `summarize_kd76.py` 镜像同一常量/规则；两侧固定向量必须一致。F11 的 `requiredSamples/gateMillis` 覆盖参数必须删除，旧单进程 20 轮入口必须改名/`@Ignore`，否则任何"PASS"都可能是伪造的。

## 2. 合法执行形状：20 轮 reboot 冷启动

### 2.1 预注册清单（跑之前写死，跑后不得改）

| 项 | 预注册值 | 依据/理由 |
|---|---|---|
| 样本量 | n=20 个**独立 boot**；closure 证据建议 10+10 两批 | R2 §2.3 #2；A6 |
| 估计量 | nearest-rank `p95 = sorted[ceil(0.95n)-1]` | R2 §2.1；仓库 Kotlin 同式 |
| 主口径 | `M = S-bind + S-warmup`（毫秒） | R2 §2.3 #1；单轮入口同式 |
| 门 | `M.p95 ≤ READY_TIMEOUT_MILLIS/2 = 5 000 ms` | R2 §3.2；`summarize_kd76.py:55-56` |
| 冷启动条件 | `mode=reboot`，`settle=0`（reboot 后不沉降） | R2 §2.3 #2 "同为 reboot 后不沉降的冷启动"；脚本默认 `SETTLE_SECONDS=0`（`:46`） |
| 轮次编号 | 全局唯一 1..20；两批为 1..10 + 11..20 | §2.6；探针 G/H |
| 失败处置 | 不重试、不补点、不删点、不缩尾、不换估计量 | R2 §3.1/A5/A7/A10 |
| 批次合并 | 只合并原始样本；条件漂移则分开报告 | R2 §2.3 #3；Prometheus 分位数不可加 |
| 证据绑定 | 同一 APK sha、同一设备指纹、同一源快照；每轮 boot_id 可证 | 计划 §4:148；批次 41 记录 F10 |

**为什么 `settle=0`**：R2 预注册的是"reboot 后不沉降"，脚本默认也是 0。E-41-D04 单轮 `loadBefore=6.49` 正是 reboot 后系统启动残余（`step04-kd76-single-round.md:69`）；这是被测量的条件的一部分，不是要洗掉的噪声。若将来要测"沉降后的冷启动"，那是另一个条件（C1b），必须单独预注册、单独报告，**不得**与 settle=0 的样本合并。

### 2.2 每轮执行步骤（宿主脚本形状）

1. **安装一次**：`adb install -r -t <app.apk>`、`<test.apk>`；记录宿主计算的 `targetApkSha256` / `testApkSha256`；记录 `sourceHead`、`sourceDirtyPaths`、设备 `fingerprint/sdk/abis/page_size`、`use_freezer`、`Apps frozen` 数。
2. **reboot**：`adb reboot` → `adb wait-for-device` → 轮询 `sys.boot_completed=1` → 轮询 `pm path <pkg>` 可用（`run_kd76_rounds.sh:199-215`）。
3. **唤醒/屏幕**：`adb shell input keyevent 224`；宿主读 `dumpsys power` 的 `mWakefulness`/`Display Power`，要求 Awake（app 侧 `runOneRound` 还会在轮首断言 `PowerManager.isInteractive`，`:413-418`）。
4. **采集宿主身份（新增，见 §5）**：
   - `adb shell cat /proc/sys/kernel/random/boot_id`（before）
   - `adb shell settings get global boot_count`
   - `adb shell pidof <pkg>`、`pidof <pkg>:visual_js`
   - `adb shell cat /proc/loadavg`
   - `adb shell dumpsys activity | grep -A20 "Apps frozen:"`（记录数量，不作门）
5. **前置断言**：`boot_id` 非空且与之前所有轮不同；`pidof <pkg>:visual_js` 为空（worker 冷）；`boot_count` 非 -1；屏幕 Awake；包已安装。
6. **测量**：`adb shell am instrument -w -e class <testClass>#readRoundFromInstrumentationArg -e smb.kd76.round N <component>`，超时 300 s（脚本 `:243-252`）。
7. **落证据**：`round-NN.am.txt`（原始输出）+ `round-NN.xml`（`<system-out>` 原样收 `KD76_ROUND/META/SAMPLE`，不补造；脚本 `:285-303`）。宿主把 boot_id/pid/load/freezer 写进 `KD76_ENV` 行（新增字段，见 §5）。
8. **后置采集**：再读一次 boot_id、`pidof <pkg>`、屏幕状态、loadavg；`boot_id_after == boot_id_before`，否则本轮 INVALID（设备在轮中重启/崩溃）。
9. **不重试**：任何失败先归因；环境归因 → 整批作废、保留原批、重跑新批；产品归因 → 记录真红，不重跑洗绿（R2 §3.3/A7）。

### 2.3 boot_id 证明（本项核心）

**定义与来源**：
- `/proc/sys/kernel/random/boot_id`：内核注释 "boot_id - a UUID representing the current boot"；proc 项 `mode = 0444`（Linux `drivers/char/random.c:1587,1690-1693`，本轮 `gh api` 实读）。
- 宿主 `adb shell cat /proc/sys/kernel/random/boot_id` 已实测可读：emulator-5584 → `12abf474-f06c-4702-893c-979ea249fdf5`；emulator-5566 → `8f54d45c-cd12-4e96-95a2-1656b3b382d1`。
- app 侧 `Settings.Global.BOOT_COUNT`：AOSP Javadoc "Boot count since the device starts running API level 24"，`@Readable`，常量值 `"boot_count"`（`Settings.java:17763-17769`，本轮 `gh api` 实读）；官方 API reference 同文（来源表 L3）。E-41-D04 实测单轮 `bootCount=2`（`step04-kd76-single-round.md:52`）。

**裁定**：
1. **主证明 = 宿主 boot_id**：20 轮 20 个不同 UUID；每轮 before/after 相同。这是计划 §4:148 "20 轮必须 boot_id 可证"的直接落实。
2. **副证明 = app BOOT_COUNT**：每轮非空、非 -1、与宿主 `settings get global boot_count` 相等；20 个值互不相同。app 读不到 `/proc/loadavg` 等（低负载研究 §2.2），但 `Settings.Global` 是 `@Readable`，且 E-41-D04 已证明该 app 能读。
3. **不提供降级**：boot_id 读不到（非 0444、权限/SELinux 拒绝、命令失败）→ 该轮 `boot_proof_missing` → NOT EVALUABLE。不要用"BOOT_COUNT 不同"单独替代 UUID 证明。
4. **force-stop 自动出局**：同一 boot 内 20 次 force-stop 的 boot_id 全相同 → 门判 NOT EVALUABLE。这正是 F10 "bootCount 无门"要消灭的失败。
5. **快照/quick boot 自动出局**：任何原因导致 boot_id 重复（快照恢复、reboot 未真正发生、设备掉线后仍同 boot）→ `boot_proof_duplicate` → NOT EVALUABLE。启动器已用 `-no-snapshot`，但门仍是最终防线。
6. **命名纠正**：计划项 25 写 "bootCount 采集（/proc/.../boot_id）"；两者不是一回事。实现应同时采集 `boot_id`（宿主）与 `bootCount`（app/宿主），不要混名。

### 2.4 "进程冻结"的四种机制与裁定

| 机制 | 事实 | 对 20 轮主口径的裁定 |
|---|---|---|
| **Cached Apps Freezer**（Android 11+） | 官方："stops execution for cached processes"；"If Android determines that an app shouldn't be doing work but might be needed in the future, it freezes the app process rather than terminating it. This prevents a cold start when the app is needed again."；"When a client binds to a service, the server process is bound to the client and is prevented from entering the cached state before the client does."（AOSP cached-apps-freezer，本轮实读） | **允许存在，不作门**。reboot 后测量前 `:visual_js` 不存在；app 进程即使被 BOOT_COMPLETED 拉起，也由 `pidof <pkg>` 位记录（本表末段），没有可冻的旧 worker；轮内绑定的服务不会被缓存冻结。记录 `Apps frozen:` 数（5584 实测 `Apps frozen: 14`）作环境元数据；不要求关闭 freezer（关闭会改变设备条件，需单独预注册）。 |
| **`am freeze <pkg>` 手动冻结** | 冻结的是**已存在的热进程**；`am unfreeze` 恢复原状态（官方诊断命令） | **拒绝作冷启动替代**。它测到的是解冻延迟，不是新 fork 的 `:visual_js` 冷启动；与 reboot 样本不可合并。 |
| **模拟器快照 / quick boot** | 保存/恢复 RAM；`tools/start-emulator.ps1:32` 已用 `-no-snapshot` | **拒绝**。快照恢复可能复用 boot_id（门会判 NOT EVALUABLE）；即使 boot_id 未复用，服务/进程状态也不是冷启动。 |
| **`am force-stop`** | 杀进程但保留同一 boot、OS 页缓存，且可能留下被冻结的缓存进程（官方 freezer 文档） | **不是主口径**。只能作非主口径 smoke；`mode=force-stop` 的 20 轮即使 n=20 也判 NOT EVALUABLE（boot_id 相同）。 |

**"冷"的准确含义**：KD-76 测的是 **`:visual_js` 隔离进程**的冷启动（worker UID ≠ instrumentation UID，单轮入口 `:450-458`），不是 instrumentation/app 进程的冷启动。app 进程可能被 BOOT_COMPLETED receiver 提前拉起（`AndroidManifest.xml:48-61`），它是 harness 侧状态；必须记录 `pidof <pkg>` 的"存在/不存在"位，并要求 20 轮该位一致；若某些轮存在、某些轮不存在，判 `condition_drift`（除非对所有轮预注册了同一种归一化，例如 boot 后统一 `am force-stop` 一次，且记录在 manifest）。

### 2.5 负载、屏幕、时钟

- **屏幕**：轮首 app 断言 `PowerManager.isInteractive`；轮尾宿主再读一次（新增）。屏幕熄灭 → `uptimeMillis` 在 deep sleep 暂停，段值会偏小（R2 A12；单轮入口 `:413-418`）；任一端不交互 → INVALID。
- **负载**：宿主 `/proc/loadavg` 每轮 before/after 记录；app 读不到 `/proc/loadavg`（低负载研究 §2.2 实测 EACCES），不要 app 侧实现 loadavg 门。settle=0 的 boot storm 是预注册条件的一部分；**不设低负载门**。两批合并时用宿主 `la1/nproc` 比较批次条件；差异明显（建议同 2× 中位数规则）→ `condition_drift`，不合并（§2.6）。
- **时钟**：段值只用同进程 `SystemClock.uptimeMillis()`（R2 A2；单轮入口 `:421` 起）；宿主 `elapsedRealtime`/墙钟只用于排序和日志。不混用 `nanoTime`/`elapsedRealtime` 计算段值。
- **温度/电量**：模拟器无真实热源（低负载研究 §2.6）；真机后续记录，不作当前门。

### 2.6 分两批合并（10 + 10）

**形状**：
- 方式 A（推荐，closure）：批 A 轮 1–10，批 B 轮 11–20；两批同 APK sha、同设备指纹、同 `mode=reboot`、同 `settle=0`、同预注册常量。
- 方式 B（统计等价，A6 未满足）：单批 20 轮。可用于出 p95 判词，但台账必须写 "single batch；A6 两批独立未满足"，不能据此关闭 KD-76。

**工具现状与最小改动**：
- `run_kd76_rounds.sh` 循环固定 `seq 1 "$ROUNDS"`（`:316`），文件名/参数都用同一个 `round`（`:234-246`）。两次 `--rounds 10` 会产出两份 `round-01..10`，汇总看到重复轮号 + 缺 11..20 → `NOT EVALUABLE`（探针 G 实测 exit 2）。
- 汇总脚本本身已支持跨目录合并：1..10 + 11..20 的 20 份 XML → `PASS`（探针 H 实测 exit 0）。所以只需给脚本加 `--first-round`（默认 1；循环 `seq $FIRST $((FIRST+ROUNDS-1))`；校验 1..20 且不越界），批 B 用 `--first-round 11 --rounds 10`。
- 两批的输出目录分开（`--out build/kd76-runs/batchA`、`batchB`），汇总时同时传两个目录；**不要**把作废批和新批混在同一目录（重复轮号）。

**合并规则**：
1. 只合并**原始 M 样本**；不得合并两批 p95，不得对 p95 取平均（Prometheus 官方："cannot aggregate quantiles"；R2 §3.4）。
2. 每批 n=10 的 p95≡max，**不是门**；不要用 5 000 ms 去卡单批。门只施于合并 n=20。
3. 两批都必须 G1 绿（无 FAIL/INVALID）；任一批有 G1 红 → 该批作废/重跑，不合并。
4. 条件漂移：两批 S-warmup 中位数比值 >2×（仓库既有先例：`VisualJsConnectStageCalibrationInstrumentedTest.kt:715-729`）或宿主 `la1/nproc` 明显不同 → 不合并，按批分别报告（n=10 只作描述）。
5. 跨批仍要求 20 个 boot_id 全不同、20 个 app bootCount 全不同且与宿主一致；同一 APK sha/设备指纹；任一轮 `boot_id` 重复 → NOT EVALUABLE。
6. 作废批保留在 evidence（原目录），不传给汇总；重跑批使用同一预注册 id 段（如批 A 重跑仍 1..10），汇总输入只含有效批 + 另一批。这样既保留"不重跑洗绿"的审计，也避免重复轮号。

## 3. 统计与判词

### 3.1 M、nearest-rank p95、报告字段

- **M**：`bindMillis + warmUpMillis`（S-bind + S-warmup）。不是 S-warmup 单段，不是 total（total 还含 readyGap + firstByte），不是四段之和。
- **p95**：`sorted[ceil(0.95*n)-1]`（0 基）。
  - n=20：`ceil(19)-1 = 18` → 第 19 个（19/20）；**恰好容忍一个最大值**。
  - n=10：`ceil(9.5)-1 = 9` → 第 10 个 = max；所以 n=10 没有离群容忍，不能当门。
  - 固定向量本轮复算：`1..20` → p95=19；`1..19 + 9999` → p95=19（9999 被容忍）。
- **必须报告**：`n_valid` / `n_fail` / `n_invalid` / `n_missing`；`min/p50/p90/p95/max`；**排序后的完整 M 向量**；每轮 `boot_id`、`bootCount`、`apkSha256`、`fingerprint`、`loadBefore/After`；FAIL 的删失下界；G1 理由；G3 max 归因。
- **不得**：只写一个 `p95=xxx` 不给样本向量；把不同 n 的 p95 比较；把线性插值（E-04 的 725）与本口径对比（R2 §2.1）。

### 3.2 门结构（G0–G3）

| 门 | 内容 | 红时的含义 |
|---|---|---|
| **G0 形状** | 每轮：fresh engine 无已开始 bind、screen interactive、`connectCount==1`、worker UID≠test UID、generation 非空且过滤生效、无重建、时间戳单调、`total == bind+warmup+readyGap+firstByte` | 记录/夹具/seam/产品路径错误；该轮 INVALID，计时无意义（单轮入口 `:404-506`；汇总 `:211-225`） |
| **G1 零未归因失败** | 20 轮中不得有 FAIL/INVALID/XML `<failure>`/`<error>`；任何失败先归因 | 真实超时/环境/夹具/快照问题；G1 红时 G2 绿也不算过（合取） |
| **G2 p95 门** | n=20、G1 绿、`M.p95 ≤ 5 000` | 余量不足 2×；按产品优化或单独的门重谈处理，不得放宽 |
| **G3 max 报数** | 必须报 max；`max > 5 000` 必须附归因 | 不单独判红；不得省略 |

### 3.3 删失（FAIL）与无效（INVALID）的区别

| 类型 | 定义 | 计入 n? | 判词效果 | 报告 |
|---|---|---|---|---|
| **SAMPLE** | 形状合法、M 可算 | 是 | 进入 p95 | 原始 M + 段值 |
| **FAIL** | `connectForTest()==false`（≥15 000 ms）或 execute 非 `Rendered`（≥2 500 ms）或超时 | 否（删失） | G1 红 → NOT EVALUABLE | 删失下界 + 归因 |
| **INVALID** | seam/夹具/时间戳/形状/元数据/boot 证明缺陷 | 否 | G1 红 → NOT EVALUABLE | 不给删失下界；整批作废 |
| **MISSING** | 无 XML / preparation failed / 无 SAMPLE 行 | 否 | n<20 → NOT EVALUABLE | 缺失轮号 + 原因 |
| **PREP_FAILED** | reboot/pm 超时，instrumentation 未开始 | 否 | n<20 → NOT EVALUABLE | `round-NN.xml` 的 `<failure>` 占位（脚本 `:321-331`） |

**规则**：
- FAIL 的值是 `≥ 预算`，不是 0、不是缺失；不丢点、不缩尾、不重跑（R2 §2.5/A5/A7）。
- INVALID 不是删失样本：它是测量系统缺陷，整批作废、修 fixture/seam 后重跑；不得把 INVALID 当"≥预算"混入分布。
- G1 红时**不出 p95**（即使是描述性 p95 也不得叫 M.p95）；只报成功轮 n、FAIL/INVALID 数、删失下界、排序成功样本（供归因）。
- `n` 的上限是 20：INVALID/FAIL/MISSING 都占用预注册槽位，按每轮的**主分类各计一次**，`n_valid = 20 - fail - invalid - missing`；不得补一轮/多跑一轮凑 20（optional stopping）。

### 3.4 PASS / FAIL / NOT EVALUABLE 与退出码

| 判词 | 条件 | 汇总退出码 | 文本 |
|---|---|---|---|
| **PASS** | n=20、G1 绿、`M.p95 ≤ 5 000`（含等于） | 0 | `G2: PASS (M.p95=... <= 5000 ms)` + G3 |
| **FAIL** | n=20、G1 绿、`M.p95 > 5 000` | 1 | `G2: FAIL (M.p95=... > 5000 ms)` |
| **NOT EVALUABLE** | 任一 NOT EVALUABLE 条件（§5） | 2 | `G2: NOT EVALUABLE — ...`；**不得出现 PASS 字样**；`no verdict may be derived` |

- `runner exit 1`（某轮 `am instrument` 失败）**不是**产品 FAIL；它产生 FAIL/INVALID 轮 → 汇总 exit 2 / NOT EVALUABLE。只有汇总 exit 1 才是 G2 FAIL。
- `max > 5 000` 但 `p95 ≤ 5 000` → 仍 PASS，但必须写 G3 归因；这是 n=20 预注册的"容忍一个最大值"，不是漏洞。
- 慢但成功的样本（如 M=9 000 ms、在 15 000+10 000 预算内）是合法样本，不是 INVALID；它可能把 p95 推过门 → FAIL，或只当 G3 max → PASS + 归因。

### 3.5 n=20 的统计含义（如实）

- `PASS` 的准确表述是"本次 20 个独立 boot 的样本中，第 19 小的 M ≤ 5 000 ms"，**不是**"p95 ≤ 5 s 已被证明"。
- iid 假设下 `P(max ≤ 真 p95) = 0.95^20 ≈ 0.358`；`P(至多 1 个超过真 p95) ≈ 0.736`。要 max 作为真 p95 的单侧 95% 上界，需 n≥59（`ceil(ln0.05/ln0.95)=59`，本轮复算）。
- 因此台账只写 "observed p95"，不写 "proven"；若将来要统计保证，扩到 n≥59 或用 bootstrap CI，而不是把 n=20 的 p95 当保证（R2 §2.4）。

### 3.6 M 与 READY_TIMEOUT 的关系裁定（计划项 30）

- `FIRST_CONNECT_TIMEOUT_MILLIS=15_000` 约束 S-bind；`READY_TIMEOUT_MILLIS=10_000` 约束 S-warmup；M 是两段之和，最坏 25 000 ms。
- 5 000 ms 门 = `READY_TIMEOUT/2`，是预注册的产品余量，**不是** M 的最坏值的一半，也不是 S-warmup 单段的门。
- **裁定：本轮不改 10 s 阈值，也不改 5 s 门。** 若 p95 红：
  1. 先看段：S-bind 主导还是 S-warmup 主导（`kd76_chain_segments.py` 同轮集合分段）；
  2. S-warmup 接近/顶到 10 s 预算 → ready 路径问题；S-bind 大 → attach/进程启动问题；M 只是两段之和，不能反推单段；
  3. 产品归因 → 记 KD-76 真红/优化；环境归因 → 整批作废重跑；**不得**为了变绿放宽门、加沉降、换 p90/插值。
- 若 p95 绿：只说明 M 的观测 p95 ≤ 5 s，**不能**据此声称 READY_TIMEOUT 可降到 5 s；S-warmup 的独立预算仍是 10 s。
- 建议报告同时给 S-bind/S-warmup 的 n/min/p50/p95/max；若某段 p95 接近其自身预算，即使 M 绿也要在证据里标注（描述性，不是新门）。

### 3.7 29.5 s 链（S1–S4）与 20 轮 M 的关系

- 20 轮只产出 C1（S-bind）与 C2（S-warmup）的分布；C3（宿主阶段 2 500 ms）/C4（死亡确认 2 000 ms）**不在** M 里。
- 用 `python -I tools/ci/kd76_chain_segments.py <run-dir> [--c3-witness-ms 2000] [--c4-max-ms ...]`：四段预算和必须 == 29 500 ms；C3 只有 KD-66 witness（≤2 000 ms，不是分布）；C4 无实测时写 UNVERIFIED；`Σ 实测 max` 只在 C4 有实测时给，且只是上界（`kd76_chain_segments.py:102-108,139-172`）。
- **禁止**：把各段 p95 相加当链 p95；拼一个"单例 29.5 s"；把 C3 witness 当 C3 实测分布（R2 §4.3–4.4）。

## 4. 空 sha / 异常轮的处置

### 4.1 空 per-round sha / fingerprint / bootCount

**当前行为（本轮探针实测）**：

| 探针 | 输入 | 结果 |
|---|---|---|
| B | 第 7 轮 `apkSha256=` 为空，其余 19 轮有 sha | **exit 0，`G2: PASS`**，`n=20/20` |
| C | 第 7 轮 `fingerprint=` 为空，其余有 | **exit 0，`G2: PASS`** |
| I | 第 7 轮无 `KD76_ROUND` 行（无 bootCount） | **exit 0，`G2: PASS`**，bootCount(s) 静默少 7 |
| J | 第 7 轮无 `KD76_META` 行（无 sha/fingerprint） | **exit 0，`G2: PASS`** |
| N | 20 轮全部无 `KD76_ROUND` 行（无 bootCount） | **exit 0，`G2: PASS`**，无 bootCount 行 |
| D | 20 轮 bootCount 全 = 9（force-stop 形状） | **exit 0，`G2: PASS`** |
| E | 20 轮 bootCount 全 = -1（不可读） | **exit 0，`G2: PASS`** |
| F | 第 19、20 轮 bootCount 都是 19 | **exit 0，`G2: PASS`** |

**根因**：`shas`/`fingerprints` 只从非空值构造（`summarize_kd76.py:363-373`），`boot_counts` 只收集不判（`:365,415-416`）；`evaluable` 只看 `reasons/g1_reasons/n`（`:375`）。所以"某一轮缺身份"被其余轮的代表值掩盖。

**处置（必须实现的规则）**：
1. **per-round 身份是硬要求**：每轮 `apkSha256`（64 hex）、`fingerprint`、`bootCount`（非 -1）、宿主 `boot_id`（UUID）必须非空；任一为空 → 该轮 **INVALID**（`metadata_missing` / `boot_proof_missing`），不是"从集合里剔除"。
2. **计入 n 上限**：该轮占用 20 个预注册槽位，`n_valid` 减 1；`n_valid < 20` → NOT EVALUABLE。**不得**整轮静默剔除后仍报 n=20，**不得**补一轮。
3. **跨轮一致性**：20 个 sha 必须两两相等且等于宿主 manifest 的 `targetApkSha256`；20 个 fingerprint 相等；20 个 boot_id 全不同且与 app bootCount 一一匹配；任一不满足 → `snapshot_mismatch` / `boot_proof_*` → NOT EVALUABLE。
4. **宿主 sha 是锚**：汇总不能只信 app 自报的 sha（app 可能漏 META 行）。主口径要求 `--apk`/`--test-apk` 传入构建产物，宿主先算 sha 写 manifest；`already-installed` 且无法证明安装字节 → NOT EVALUABLE。
5. **空 sha 不是"删除该轮"**：计划项 5 的"不整轮剔除（标 INVALID 并计入 n 上限）"应理解为"不把该轮从 20 个槽位里删掉后假装 n=20"；正确做法是保留该轮、判 INVALID、`n_valid<20`。

   - bootCount=-1/重复 → NOT EVALUABLE（当前 E/F 红）。
   - 两批 1..10 重复 → NOT EVALUABLE；1..10 + 11..20 → PASS（当前 G/H 已分别是 2/0，可作为 fixture）。
   - `decide` 覆盖参数 → 编译失败/不存在（当前 F11 红）。
7. **跨实现一致性**：Kotlin `decide` 与 Python `summarize` 用同一组固定向量（n=20/green/5000→PASS；n=19→NOT_EVALUABLE；g1Red→NOT_EVALUABLE；p95=5001→FAIL）；两侧测试各自钉住，任何一侧改常量必须同时改另一侧（`Kd76ReportVerdictTest.kt`、`test_summarize_kd76.py:160-168`）。

## 7. 未验证 / 边界（如实）

1. **20 轮实跑未发生**：本轮零 reboot、零 `am instrument`；`n/p50/p95/M` 均不存在。E-41-D04 只有 n=1。
2. **boot_id 跨 reboot 变化未在本轮实测**：本轮只在两台在跑模拟器上做了只读 `cat`（5584/5566 各一个 UUID），没有 reboot（共享设备，避免干扰他线）。内核源码 L1 声明其语义；门必须在实跑时逐轮证明。
3. **app 侧读 `/proc/sys/kernel/random/boot_id` 未验证**：`run-as`（`runas_app` 域）可读，但不等价于正式 app 的 `untrusted_app` 域；本方案不依赖它，宿主通道已实测可读。
4. **Cached Apps Freezer 的逐轮影响未量化**：只读到 5584 `Apps frozen: 14` 与 `use_freezer=null`；未做"关 freezer vs 开 freezer"的 A/B。按官方文档与 reboot 形状，判定其不冻结目标；实跑时记录数量供归因。
5. **BOOT_COMPLETED receiver 是否在 reboot 后拉起 app 进程未实测**：只读 manifest 确认 receiver 存在；实跑必须记录 `pidof <pkg>` 位，否则 `condition_drift` 无法判。
6. **两批合并的 `--first-round` 未实现**：本轮只证明"汇总能接受 1..20 跨目录"（探针 H）与"两次 1..10 会冲突"（探针 G）；脚本改动归 WS3 实现。
7. **Kotlin 侧未跑 Gradle**：`Kd76ReportVerdict` 的 JVM 用例未在本轮执行（共享纪律：Gradle 只在门禁阶段串行跑）；本轮只实读代码 + 跑 Python 工具测试（8+6 通过）。
8. **arm64/真机/16 KB page**：全部未验证；本项是 x86_64/API 34 模拟器口径的执行形状，真机需重做 boot_id/屏幕/freezer 可读性核查。
9. **`uptimeMillis` 的屏幕熄灭偏小**：本方案用"轮首 app 断言 + 轮尾宿主检查"防；轮尾检查是新增建议，未实现、未实测。
10. **`settle=0` 的 boot storm 对 p95 的影响**：未知；这是预注册条件，不能看到数据后改成沉降。若 p95 红，先归因，不事后改条件。
