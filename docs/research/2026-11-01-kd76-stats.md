## 0. 结论摘要（pick）

1. **分位口径必须钉死为 nearest-rank（ceil）**：与仓库现有 Kotlin 门同一实现（`GoldenRetrievalInstrumentedTest.kt:605-610`，`index = ((n*p+99)/100 - 1)`）。在该约定下 **n=10 时 p95 ≡ max**（第 10/10 个样本），n=20 时 p95 = 第 19/20 个（只容忍一个最大值离群），n=40 才容忍两个。计划写的是"n≥10"，**10 是下限而不是 p95 门的充分样本量**。
2. **建议门样本 = 两批独立冷启动各 10 轮、合并原始样本 n=20**（预注册；两批同条件才可合并）。合并后 p95 = 19/20，单次离群不单独决定门；两批又各自满足 KD-66 的"两轮独立"先例。若设备成本只允许一批，则单批 n=20 等价；若只能 n=10，必须显式声明"p95 即 max 门"，否则会与 anti-flaky 的"单点离群不红"自相矛盾。
3. **E-04 的 p95=725 是线性插值，不是 nearest-rank**：本轮用 E-04 §3.1 的 10 个原始样本复算——线性插值 p50=686.00 / p95=724.95（与 E-04 逐位一致），nearest-rank p50=680 / p95=738，相差 13.05 ms（1.77%）。**两套约定不可混用、不可跨 n 比较**；KD-76 的 evidence 必须打印口径名与排序后的原始样本。
4. **outlier 不删、不缩尾、不重跑到绿**：失败/超时轮次记为**删失样本（≥ 预算）**并触发独立硬门（G1：零未归因失败），不是"缺失值"；任何决定门的离群样本先归因（环境/产品/夹具/快照）再判定，环境归因 → 整批作废重跑并保留原批，产品归因 → 真红。
5. **29.5 s 只能按"预算包络"相加**：15 000 + 10 000 + 2 500 + 2 000 = 29 500 ms 是路径上各段预算之和，是**上界（supremum）**，不是任何单例的实测值。实测只能加**同一轮集合上的各段 max**（上界），**不能加 p50/p95**（分位数不可加）。四段顶满的单例结构性不可达：C1 超时即终止路径；C2 超时只接 C4、不进 C3；C3 要求前两段成功。拼接四段满额 = 夹具接力，不做。
6. **anti-flaky 十二条**（§5）：归因先行、单钟 `uptimeMillis`、无扣除、相对门、失败不丢、两轮独立、不重试洗绿、同轮元数据、披露 100 ms 轮询分辨率、预注册、冷启动不预热、屏幕/睡眠可观测。
7. **参考评分**：仓库内 Kotlin percentile helper + KD-66 用例最高（直接复用）；HdrHistogram、LatencyUtils 高（直方图可加/协调遗漏语义参考，不引入）；macrobenchmark 中高（只借"min/median/max + 环境控制"方法）；t-digest 中（不引入）；Prometheus 官方文档作为"分位数不可聚合"的权威依据。

## 2. n≥10 冷启动轮的分位数口径

### 2.1 两套约定，必须先选一套

分位数没有唯一标准：NIST 手册明确写"There is not a standard universally accepted way to perform this interpolation"（[NIST 7.2.6.2](https://www.itl.nist.gov/div898/handbook/prc/section2/prc262.htm)，本轮实读）。仓库内同时存在两种：

- **nearest-rank（ceil）**：`p` 分位取排序后第 `ceil(n*p/100)` 个样本，值一定是**实际观测值**；`GoldenRetrievalInstrumentedTest.kt:605-610` 即此式。
- **线性插值**：`pos = q*(n-1)` 后在相邻样本间插值；`figure_eval_gate.py` 与 `retrieval_significance.py` 即此式，E-04 的 725 也是此式。

**E-04 复算（本轮 Python，命令见 §8）**：样本 `[652, 655, 678, 678, 680, 692, 694, 703, 709, 738]`
- 线性插值：p50 = 686.00，p95 = 724.95 → 与 E-04 的 686/725 逐位一致；
- nearest-rank：p50 = 第 5 个 = 680，p95 = 第 10 个 = **738**；
- 差 13.05 ms（1.77%）。

**裁定**：KD-76 校准统一用 **nearest-rank**。理由：① 与仓库内设备门的 Kotlin 实现同源；② p95 一定是观测到的样本，不制造插值点；③ 在 n=20 时恰好获得"容忍一个最大值"的可预注册性质（§2.2）。**禁止**把 E-04 的 725 与 KD-76 的 nearest-rank p95 直接对比——那是两套估计量。

### 2.2 n 与 p95 的秩：n≤19 时 p95 就是 max

| n | p95 秩 `ceil(0.95n)` | p95 秩之上可容纳的样本数（离群容忍） | 说明 |
|---:|---:|---:|---|
| 10 | 10 | 0 | **p95 ≡ max** |
| 15 | 15 | 0 | p95 ≡ max |
| 19 | 19 | 0 | p95 ≡ max |
| **20** | **19** | **1** | p95 门的最小可用样本量（容忍一个最大值） |
| 30 | 29 | 1 | |
| 40 | 38 | 2 | 容忍两个离群 |
| 60 | 57 | 3 | |
| 100 | 95 | 5 | |

（本轮 Python 逐 n 实算，§8。式子与 `GoldenRetrievalInstrumentedTest.kt:605-610` 相同。）

**直接后果**：计划里"n≥10 → p95 ≤ 5 s"在 n=10 时**字面上是 max 门**。E-04 在 n=10 下报 p95=725 之所以看着比 max 738 小，正是因为用了线性插值；换成仓库的 Kotlin 约定就是 738。若 evidence 不声明口径，读者会把两个数当成同一统计量——这是必须先钉死的原因。

### 2.3 主口径裁定（给 T4/T5 的可执行规则）

1. **统计量**：`p95 = sorted[ceil(0.95*n) - 1]`（nearest-rank）。同时报 `n / min / p50 / p90 / p95 / max` 与**排序后的完整样本向量**（R4 evidence 最低要求之上，便于任何人复算）。
2. **样本量**：默认 **两批独立冷启动各 10 轮，合并原始样本 n=20**（预注册；两批同 APK/同源快照/同为 reboot 后不沉降的冷启动）。单批 20 轮在**分位数**上与合并 n=20 等价，但不满足 A6 的"两轮独立"；关闭/维持证据仍建议两批。只有 10 轮时，报告必须显式写"n=10 下 p95≡max，本门为 max 门"。
3. **合并规则**：只在同条件、同快照、两批环境记录均正常时合并**原始样本**；**不得**合并两批的 p95（§3.4）。任一批出现未归因失败 → 该批作废重跑（§3.3），不与另一批合并。若两批的中位数相差 >2× 或 `loadavg` 明显不同，视为条件漂移：不合并，按批分别报告。
4. **门**：G2 = `p95 ≤ READY_TIMEOUT_MILLIS / 2`（现 5 000 ms；1/2 因子沿用 R2 §3.2 建议值，最终数值归主会话）。**不得**为了让门通过而改用线性插值、改用 p90、或删点。
5. **落码建议**：校准用例内放一个 5 行的 `percentileNearestRank`，并在使用前用固定向量自检（如 `0..9`：p50=4、p95=9），防止运行期换了估计量；evidence 打印口径名与排序样本。**不要**在 evidence 里只写一个"p95=xxx"。

### 2.4 小样本不确定性：p95 是点估计，不是上置信界

在 iid、连续分布的假设下，`n` 个样本中超过真 q95 的个数 ~ `Binomial(n, 0.05)`。本轮 Python 实算：

| n | P(没有样本超过真 q95) = 0.95^n | P(至多 1 个超过) | 含义 |
|---:|---:|---:|---|
| 10 | 0.5987 | 0.9139 | 60% 概率样本 max 仍低于真 p95 |
| 20 | 0.3585 | 0.7358 | 36% 概率 max 低于真 p95；p95(19/20) 约 74% 概率不高于真 p95 |
| 40 | 0.1285 | 0.3991 | |
| 59 | **0.0485** | 0.1991 | **只有 n≥59，样本 max 才可作为真 p95 的单侧 95% 上界** |

（`ceil(ln 0.05 / ln 0.95) = 59`，§8 实算。）

**结论（如实）**：n=10/20 的校准**不能证明**"p95 ≤ 5 s"这个分布命题；它只能做**筛选**。之所以仍可接受，是因为预算余量是数量级的（E-04 服务端口径 p95≈0.7 s 对 10 s 预算 ≈14×；即便客户端可感口径放大数倍，离 5 s 仍有大余量）。所以：
- 报告写"本轮 n=20 的样本 p95 = X ms"，**不写**"p95 已证明 ≤ 5 s"；
- 若将来要求统计保证，样本量按 §2.2/§2.4 加到 n≥59（max 作上界）或用 bootstrap CI，而不是把 n=20 的 p95 当保证；
- 冷启动分布可能按负载分层（E-01d 在负载 5.25 下 attach 4.6–7.5 s；E-03 轻载 loadavg 0.75），**按条件分层报告**（C1 轻载 / C2 负载），不跨条件合并。

### 2.5 失败轮 = 删失观测，不是缺失值

一个"没在 10 s 内 ready"的轮次，真实值是 `≥10 000 ms`（下界已知），不是"没有数据"。把它丢掉再算 p95，等于只统计成功轮——这正是 LatencyUtils README 描述的 **coordinated omission**：暂停/失败发生在计时窗口之外时，记录里不会出现长延迟，统计因此系统性偏乐观（[LatencyUtils README](https://github.com/LatencyUtils/LatencyUtils)，本轮实读其 "The problem" 一节）。HdrHistogram 的 `recordValueWithExpectedInterval` 也是为修正"漏采样本"而存在（[HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram)，本轮实读 "Corrected vs. Raw" 一节）。

**规则**：
- 任何未 ready / bind 失败 / execute 非 `Rendered` 的轮次，记为 **FAIL（删失，值 ≥ 对应预算）**，进入样本表与计数；
- **记录无效（INVALID）另算**：`started()==false`、时间戳非单调（`bindConnectedAt < bindRequestedAt` 等）、`connectionCountForTest()!=1` 属于 seam/夹具缺陷，不是产品延迟——该轮无效、整批作废，修夹具/seam 后重跑，**不得**当作删失样本混入分位数；
- FAIL 触发独立硬门 **G1**（§3.3），**不能被 p95 门吸收**——否则 n=20 里一个 10 s+ 的超时会被 19/20 的 p95 掩盖；
- 报告同时给"成功轮 n / FAIL 数 / INVALID 数 / 删失下界"，不允许只给成功轮的分位数。

## 3. outlier 处理

### 3.1 禁止清单（硬规则）

1. **不删点**：不因"看起来像环境抖动"删除任何样本；不缩尾（winsorize）、不截尾（trim）、不换 trimmed mean。
2. **不重跑到绿**：红 → 归因 → 处置；环境归因的整批作废重跑，原批保留在 evidence；产品归因的真红不得靠重跑洗掉。
3. **不事后改口径/样本量**：n、估计量、门、outlier 规则在跑之前预注册；不得看到数据后从 p95 换成 p90、从 nearest-rank 换成插值、从 n=10 加到"看起来够"为止（optional stopping）。
4. **不跨 n 比较 p95**：n=10 的 p95 是 max，n=20 的 p95 是第 19 个；"从 738 降到 700"可能只是估计量变了，不是性能变了。
5. **不把失败轮当缺失**（§2.5）。

### 3.2 预注册的 flag 与归因树

**flag（只用于分诊，不用于剔除）**：
- **门决定样本**：某个样本去掉后 G2 由红转绿（或反之）——该样本必须在判定前完成归因；
- **尾部候选**：样本 `> 3 × 合并 p50`（描述性阈值；冷启动右偏，3× 只是提示，不是剔除线）；
- **删失样本**：FAIL，值记 ≥ 预算，直接进 G1。

**归因树（顺序执行，结果写进 evidence）**：
1. **快照/批次**：APK sha256、源快照、设备指纹、page size 是否与同批一致？不一致 → 该批作废。
2. **环境**：轮次前后 `loadavg`、是否有其他套件/进程在跑、屏幕是否熄灭、模拟器 I/O 是否异常？异常且与离群同窗 → 环境归因。
3. **logcat 锚点**：`Start proc …:visual_js` → `warm-up finished` 的间隔；watchdog `hard deadline … killing the worker` 行；`death was not confirmed` 告警。服务端装载正常但 S-warmup 大 → 客户端轮询/调度；warm-up finished 本身就晚 → 服务端装载/资源竞争。
4. **seam 分段**：S-bind、S-warmup、S-ready-gap、S-firstbyte 哪一段主导？与 E-04 服务端口径的差 = bind/握手排队段。分段能定位的，不叫"不明抖动"。
5. **夹具**：本轮是否用了 `DelayedAttachContext` / `NotReadyWorkerContext` 等注入？注入值是否泄漏进校准轮（校准轮不允许注入）。
6. **判定**：环境 → 整批作废重跑；夹具 → 修夹具后重跑；快照 → 作废；产品 → 真红，按 KD-76 登记，不改门。

### 3.3 门结构（G0–G3，建议 T4 照此写断言顺序）

| 门 | 内容 | 红时的含义 |
|---|---|---|
| **G0 归因先行** | 先断言轮次形状：`started()`、时间戳单调、`connectForTest()` 成功、首个 execute `Rendered`、`connectionCountForTest()==1`；形状不对先红（INVALID，整批作废），且不进入计时判读 | seam/夹具/产品路径错误，计时数字无意义 |
| **G1 零未归因失败** | 成功轮之外不得有 FAIL；任何 FAIL 必须已按 §3.2 归因为环境/夹具（→ 批作废重跑）或产品（→ 真红） | 冷启动真实超时；不得被 p95 吸收 |
| **G2 p95 门** | 合并样本 nearest-rank `p95 ≤ READY_TIMEOUT/2` | 余量不足 2×，按 R2 §3.2 的调参/上报档处理（最终数值主会话裁） |
| **G3 max 报数** | `max` 必须报出；`max > G2` 时必须附归因 | 不单独判红；但不得省略 |

G1 与 G2 是**合取**：G1 红时 G2 绿也不算过。这样既保留"单次离群不单独决定 p95 门"（n=20 容忍一个 max），又不让真实超时被 p95 掩盖。

### 3.4 跨轮/跨条件合并

- **禁止平均分位数**。Prometheus 官方文档明确："you cannot aggregate quantiles (e.g. to calculate the total 90th percentile latency for a service backed by multiple replicated workers)"，且"averaging the quantiles yields statistically nonsensical values"（[Prometheus: Histograms and summaries](https://prometheus.io/docs/practices/histograms/)，本轮实读）。
- **要合并就合并原始样本**，且仅在同条件、同快照、预注册时；HdrHistogram README 说明直方图是**可加的**（"since Histogram objects are additive, it is common practice to … perform histogram aggregation math across time and/or threads"）——可加的是**桶/原始样本**，不是已经算出来的分位数。
- C1（轻载冷启动）与 C2（冷启动 + CPU 竞争）是不同条件，**分别报告**，不合并；如需一个"总体"数，报告两条件的 p95 与 max 并列，不给加权平均。

### 3.5 边界样本（ready 恰在期限附近）

`readyAt` 在 `awaitWorkerReady` 的两处成功出口写入（`:821`、`:840`），其中 `:840` 是"期限到点那一刻 `isReady()` 仍为真"的边界出口。若某轮 S-warmup 落在预算的 1 个轮询间隔（100 ms）内，它不是 FAIL，但必须作为**边界样本**单独标注：这说明"慢但会到"，与"超时"是两种形状；归因时不得混为一谈。

## 4. 29.5 s worst-case 链：四段相加规则与不可拼单例论证

### 4.1 链的四段（C1–C4）与代码锚点

为避免与 seam 的 `S-bind/S-warmup/S-ready-gap/S-firstbyte` 混淆，本文把契约链的四段记作 **C1–C4**（对应任务口径的 S1 bind / S2 warmup / S3 宿主阶段 / S4 死亡确认）。

| 链段 | 语义 | 预算 | 代码锚点 | 备注 |
|---|---|---|---|---|
| **C1** bind/首连 | `bindService` → CONNECTED 发布 | 15 000 ms | `VisualJsClientEngine.kt:1301`；seam `bindRequestedAt`→`bindConnectedAt`（`:670`→`:1161`） | 超时走 loading 分支并**终止本次执行**（`:712-737`），不进入 C2 |
| **C2** warm-up ready | CONNECTED → `isReady()` 首真 | 10 000 ms | `:1325`、`:1328`；seam `bindConnectedAt`→`readyAt`（`:1161`→`:821`/`:840`） | 客户端可感投影段（服务端 warm-up 早于握手开始）；轮询粒度 100 ms |
| **C3** 宿主阶段 | `runSession` 被 `withTimeout(2 500)` 包住 | 2 500 ms | `VisualJsClientEngine.kt:271`；`VisualExecutionEngine.kt:129` | 超时 → `catch TimeoutCancellationException` → `NonCancellable { abandon }`（`:280`） |
| **C4** 死亡确认 | `abandon` → `awaitDeathConfirmation` 返回 | 2 000 ms | `VisualJsClientEngine.kt:847-856`、`:889-895`；常量 `:1314` | **两条路径都会走到**：C2 超时后的 loading 收尾也调用 `abandon(candidate)`（`:786`）；C3 超时后的 `NonCancellable` 放弃同样走它（`:280`）。C1 超时分支不调用 `awaitDeathConfirmation`，不付 C4 |

**一处对既有 R2 表述的修正**：R2 §4.2 说"attach 满额超时后不会再有同 link 的 ready 等待"——对 C1 正确；但 **C2 超时本身会触发 C4**（`:764-792` 的未 ready 分支在 `:786` 调 `abandon(candidate)`），所以"C2+C4 可共存，C1 超时则全部终止"才是完整形状。这不改变包络结论，但改变"哪些段能在同一路径出现"的枚举。

### 4.2 seam 的四段 ≠ 链的四段

| seam 段 | 起→止 | 与链段的关系 |
|---|---|---|
| S-bind | bindRequested → bindConnected | **= C1** |
| S-warmup | bindConnected → ready | **= C2**（客户端投影口径） |
| S-ready-gap | ready → execute ACCEPTED | **⊂ C3**（C3 还包含派发、首字节、payload 全量读与解码） |
| S-firstbyte | ACCEPTED → 结果首字节 | **⊂ C3**；只在成功路径写，超时路径为 0 |

因此：**不要把 seam 的 S-firstbyte 当成 C3 的实测值**，也不要把 S-ready-gap+S-firstbyte 相加当成 C3；C3 的边界是 `withTimeout(2 500)`，不是首字节。seam 的用途是拆分 C1/C2 与定位 C3 内部，不是重定义链。

### 4.3 相加规则（哪些能加、哪些不能）

| 量 | 能否相加 | 规则与理由 |
|---|---|---|
| **预算常量** | **能** | 路径上遍历的各段预算之和是上界：`L ≤ Σ budget_i`。29 500 ms 即此包络；它是 **supremum**，不是可达实测值（§4.4） |
| **同轮集合的实测 max** | **能（给上界）** | 对同一批轮次，`max_j (Σ_i x_i,j) ≤ Σ_i max_j x_i,j`。把各段实测 max 相加，得到链观测 max 的**上界**；不是等式，可能偏保守 |
| **实测 p50 / p95** | **不能** | 分位数不可加：`p95(X+Y) ≠ p95(X)+p95(Y)`；即使 X、Y 独立，和的分位数也由联合分布决定。Prometheus 官方文档明确"cannot aggregate quantiles"；可加的是桶/原始样本（HdrHistogram README） |
| **跨轮/跨条件的分位数** | **不能平均** | 见 §3.4；要合并就合并原始样本 |
| **删失段** | **按预算计入** | 删失轮的可感时长在预算点终止（按预算计）；底层未完成时长 ≥ 预算，不进求和。不要把它当 0 |

**报告口径**：
- 名义包络：`Σ budget = 29 500 ms`（契约 `:72` 的算术，不是实测）；
- 经验上界：`Σ 各段实测 max（同轮集合，能同轮的优先同轮）+ Binder/调度开销观测`；
- **禁止**出现"链 p95 = 各段 p95 之和"或"实测 29.5 s"。

### 4.4 为什么不能拼一个"单例 29.5 s"

1. **C1 顶满即终止**：C1 在 15 s 超时后走 loading 分支并返回（`:712-737`），不会再有 C2/C3/C4。所以"C1=15 s 且 C2=10 s"在同一执行里不可能。
2. **C2 顶满只接 C4**：C2 在 10 s 超时后调用 `abandon(candidate)`（`:764-792`，调用点 `:786`），付 C4（≤2 s），但不进入 C3。所以"C2=10 s 且 C3=2.5 s"不可能。
3. **C3/C4 顶满要求前两段成功**：要走到 C3，C1、C2 必须**严格小于**各自预算；要 C3 顶满 2.5 s 再 C4 2 s，前两段已经成功。于是"四段同时顶满"要求的条件互相排斥。
4. **拼接只能靠夹具接力**：要在一支测试里依次看到 15 s、10 s、2.5 s、2 s，必须在第一个超时后重建 engine/link 再注入下一段——测到的是**测试作者选的注入常量之和**，不是产品路径的分布；换一组注入值就换一个"29.5 s"，循环论证。
5. **结论**：29 500 ms 是**预算包络的上界**（supremum），可用"预算相加"证明；单例端到端 29.5 s **不是必须复现的断言**，也不应作为验收门。计划任务 5 的"分段相加报告，禁拼单例端到端"与此一致。

### 4.5 C3、C4 的实测怎么报

- **C3**：用既有 KD-66 门 `aHungWorkerReleasesTheCallerWithinHardPlus500ms`（`VisualJsIsolationInstrumentedTest.kt:479-541`）的 `elapsed`（t_submit→t_return）作**witness**：它证明在 #240 挂死形状下调用方 ≤ `hard+500 = 2 000 ms` 有界返回（设备三轮绿，`known-defects.md:2619`）。**这不是 C3 的实测替代**：该形状不经过 C4，且 2 000 ms 是"hard+500"的上界，不是 2 500 ms 宿主期限的实测分布。报告写法：`C3 witness ≤ 2 000 ms（KD-66 门，n=3 设备绿）；C3 预算 2 500 ms（未单独做宿主期限打满的分布实测）`。
- **C4**：用 `abandonForTest()`（`:1205`）前后夹 `uptimeMillis`，记录墙钟与 `confirmed` 布尔；同时保留 logcat 的死亡确认事实。**现状：C4 没有 ms 级实测分布**——批次 24 的 6/6 是行为绿，`:850-853` KDoc 明确"AOSP 不承诺 `binderDied` 的延迟上界，仓库也无毫秒级 death 延迟实测；E-01b 的 16 ms 是 attach→SIGKILL，不是 death 延迟"。因此 C4 目前只能报"≤ 2 000 ms 预算 + 行为绿"，毫秒分布 UNVERIFIED。
- **C1/C2**：冷启动轮 seam 实测（n=20 合并样本，§2.3）。S-warmup 有 0–100 ms 的轮询量化偏差（`:1328`），报告注明"量化上限 100 ms"。

## 9. 未验证项（如实）

1. **未跑 Gradle / 未跑设备**：本文所有判据、门、样本量均为设计面；READY_TIMEOUT 校准数字、29.5 s 各段实测值**不存在**（E-08：androidTest 0 引用，校准载体未落码）。共享纪律"不运行 Gradle（门禁由脚本串行执行）"。
2. **n=20/59 的二项覆盖计算**：基于 iid + 连续分布假设；真实冷启动轮存在预热/热漂移/负载相关，非严格 iid。该表只用于说明"小样本 p95 不是上界"的量级，不作为正式置信区间。
3. **C4 的毫秒分布**：不存在。只有 `DEATH_CONFIRM_TIMEOUT_MILLIS=2_000`（产品选择）与批次 24 的 6/6 行为绿；KDoc `:850-853` 明说无 ms 级 death 延迟实测。
4. **C3 的"宿主期限打满 2 500 ms"分布**：不存在。只有 KD-66 `hard+500 ≤2 000 ms` 的 witness（且该形状不经过 C4）。
5. **官方 SystemClock 页面**：本轮 `developer.android.com` 抓取被页面导航噪声截断，未逐字取到 `uptimeMillis`/`elapsedRealtime` 的原文句；时钟语义沿仓库内 KD-66 设计 `:104-109` 的既有双源裁定，A12 的"官方原文逐字"仍 UNVERIFIED。
6. **计划判据 1/2 因子的最终数值**：归主会话裁定（R2 §3.2 原文"≥2× 是本研究的建议值……最终数值由主会话裁定"）；本文只钉统计量，不改数值。
7. **seam 设备绿绑定**：E-08 记录 isolation 三窗红未收敛、T4 关联不可证伪；seam 落码后的隔离套件复绿仍未取得（R2 §7.6 的绑定前提不成立）。本文的统计口径不改变该前置。
8. **arm64 / 真机 / 低内存口径**：沿 E-04 §6 与 KD-76 既有缺口，全部 UNVERIFIED；本文数字仅为 x86_64/API 34 模拟器口径的设计参照（且尚未出数）。
