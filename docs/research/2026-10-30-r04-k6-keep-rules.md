# R-04 K6 keep 规则研究（2026-10-30）：`j$/util/g` 名称冲突与 `androidx.tracing.Trace` 缺类机制、最小 keep 方案、K6 重跑判据

> 研究人：R8/ProGuard 混淆研究员（子代理，R8keep）。驱动批次 36 计划任务 1（T1/T2）。
> 方法：本会话实读 + 实跑（sha256sum、unzip、dexdump、mapping 检索、POM 下载、gh CLI、WebFetch/web_reader）。
> 所有机制结论均来自对**崩溃当次产物对**（两 APK sha 与 `build/device-track-batch35/r04-two-apk-sha.txt` 逐字一致，本会话实核）的 dex/映射层取证，不是推测。

## 0. 一句话结论

K6 的三类崩溃签名是**同一根因的两个面**——minified 主 APK 与 minified 测试 APK 在同一 instrumentation classloader 里按"测试 dex 在前、主 dex 在后"合并（logcat `:46`/`:53`），而两 APK 由**两次独立 R8 运行**产出、无任何改名协调：

1. **`NoSuchMethodError j$/util/g <init>(Ljava/util/Map;)V`**：主包 R8 把 `j$.util.DesugarCollections$SynchronizedMap` 改名为 `j$/util/g`（主 mapping `:871393`），测试包 R8 把 `j$.util.Comparators$NaturalOrderComparator` 改名为**同一个** `j$/util/g`（测试 mapping `:49004`）；运行时主包 `j$.util.DesugarCollections.synchronizedMap` 对 `j$/util/g;-><init>(Ljava/util/Map;)V` 的调用解析到测试 dex 的**枚举 Comparator**（无该构造器）→ 炸。**这可以也只能在 `app/r04-test-keep.pro` 修**。
2. **`NoClassDefFoundError / ClassNotFoundException: androidx.tracing.Trace`**：主包 R8 把 `androidx.tracing.Trace` 整类**内联并删除**（主 mapping 内联帧记录，主 dex 0 定义）；测试 APK 因 AGP 不重复打包主包已提供的共享依赖而**从未装载它**（测试 dex 0 定义、0 mapping 条目）；测试 dex 里 `androidx.test.**`（被 r04 规则 3 保名）按原名引用它 → 悬空。**`app/r04-test-keep.pro` 里任何 keep 都修不了它**——类不在测试 R8 输入里，keep 无法凭空造类；必须在主包 `app/proguard-rules.pro` 保类（或等价依赖侧处置，§五）。

计划任务 1 的前提"对 androidx.tracing.Trace 与 j$/util/g 扩 `app/r04-test-keep.pro`"**一半成立一半不成立**：`j$` 半边在该文件修；`androidx.tracing.Trace` 半边结构性不可能在该文件修，须另落点（§五.2，归主会话/实现轨裁定）。

## 二、机制一（已证）：`j$/util/g` 是**两次独立 R8 的混淆名碰撞**

### 2.1 证据链（每步本会话实跑）

1. **主包侧**：`app/build/outputs/mapping/strictOfflineRelease/mapping.txt:871393`
   `j$.util.DesugarCollections$SynchronizedMap -> j$.util.g:`
   主包 `classes2.dex` 中 `Lj$/util/g;` 类定义（dexdump）：`PUBLIC FINAL`、super `Object`、实现 `java.util.Map`+`Serializable`+`j$.util.Map`、实例字段 `a:Ljava/util/Map;`、Direct methods 首个即 `'<init>' type '(Ljava/util/Map;)V' PUBLIC CONSTRUCTOR` —— 就是 SynchronizedMap，**有**那个构造器。
2. **测试包侧**：`app/build/outputs/mapping/strictOfflineReleaseAndroidTest/mapping.txt:49004`
   `j$.util.Comparators$NaturalOrderComparator -> j$.util.g:`
   测试包 `classes2.dex` 中 `Lj$/util/g;` 类定义（dexdump）：`PUBLIC FINAL ENUM`、super `java.lang.Enum`、实现 `java.util.Comparator`、static `INSTANCE` —— **没有** `<init>(Ljava/util/Map;)V`（枚举只有 `<init>(Ljava/lang/String;I)` 与 `<clinit>`）。
   测试 mapping **不含** `DesugarCollections$SynchronizedMap` 条目（grep 空）——该类在测试 dex 里根本没被编译进去（测试侧无 `synchronizedMap` 调用者，被收缩），名字 `j$/util/g` 因此被改名器重新分配给别的类。
3. **运行时解析顺序**：`r04-k6-logcat.txt:46`（`Configuring clns-6 for other apk /data/app/…offline.test…/base.apk:/data/app/…offline…/base.apk`——**测试 APK 在前**）与 `:53`（合并 classpath `PCL[test/base.apk:test/!classes2.dex:app/base.apk:app/!classes2.dex]`）。
4. **崩溃调用点**：`r04-k6-logcat.txt:87-89`：`j$.util.DesugarCollections.synchronizedMap`（主 dex 类，全名保留）← `androidx.work.impl.WorkDatabase.<init>` ← `WorkManagerInitializer`（androidx.startup 反射实例化）。类名 `j$.util.DesugarCollections` 测试 dex **没有**（字符串检索 0 命中）→ 解析到主包自己的副本；它内部 `new j$/util/g(map)` 的类名查找则命中**测试 dex 的枚举**（在前）→ `NoSuchMethodError`，与 `:86` 报文（"declaration of 'j$.util.g' appears in …offline.test…/base.apk!classes2.dex"）逐字吻合。
5. **"4×" 勘误**：`:86/:141/:240/:274` 是**同一次失败**（同 PID 21982、同栈）经 4 条日志通道（W AndroidJUnitRunner / E MonitoringInstr / E AndroidRuntime crash 段 / D MonitoringInstr）各渲染一遍，不是 4 个调用点。
6. **无改名协调的直接证据**：同一原始类 `j$.util.Comparators$NaturalOrderComparator`，主包映射到 `j$.util.e`，测试包映射到 `j$.util.g` —— 两次 R8 运行各自独立分配短名；`build.log`（r04-step1/step2）grep `applymapping` = 0 命中。AGP 的 `testProguardFiles`（"Adds proguard rule files to be used when processing test code"，官方 DSL 文本已核，§七.1）只合并**规则**，不合并/协调**改名结果**。

### 2.2 对计划提问的勘正

计划问"j$/util/g（desugared java.util.LinkedHashMap$Entry?）"——**不是** LinkedHashMap$Entry：主包语义 = `j$.util.DesugarCollections$SynchronizedMap`，测试包语义 = `j$.util.Comparators$NaturalOrderComparator`（两份 mapping 实证）。`j$/util/g` 这个"类名"本身是 R8 改名产物，两个 APK 里它是**两个不同的类**。

### 2.3 伴生观察（非崩溃因）

`:57-59` 三条 hidden-API 拒绝（`Collections$SynchronizedCollection;->mutex` 等反射 denied）出现在 `synchronizedMap` 报错前一毫秒，属 desugar `Collections` 同步包装器的反射回退路径；本次 fatal 依栈是构造器 NoSuchMethodError，denial 的独立影响 **UNVERIFIED**（§八）。

## 三、机制二（已证）：`androidx.tracing.Trace` 在两个 APK 里**都不存在**

### 3.1 谁引入、谁引用（对计划第一问的回答）

- **引入链（依赖侧）**：`androidx.work:work-runtime(-ktx):2.10.5` 的 POM（本地 Gradle 缓存实读）声明 `androidx.tracing:tracing-ktx:1.2.0` **scope=runtime**；`app/gradle.lockfile:162-163` 佐证（`tracing(-ktx):1.2.0`）。即：**WorkManager 2.10.5 引入 androidx.tracing**。
- **引用方（代码侧）**：`androidx.test:monitor:1.8.0` POM（dl.google.com 实下）声明 `androidx.tracing:tracing:1.1.0` **scope=compile（=api）**。测试 dex 中 30 处 `androidx.tracing` 引用**全部**指向 `Landroidx/tracing/Trace;`，三个方法签名：`beginSection:(Ljava/lang/String;)V`（11×）、`endSection:()V`（18×）、`forceEnableAppTracing:()V`（1×）；引用者含 `androidx.test.core.app.ActivityScenario` 与 `androidx.test.platform.tracing.AndroidXTracer$AndroidXTracerSpan`（dexdump 定位）。
- **"为何 keep 缺失"的正确答案**：不是"哪个 keep 漏写了"，而是**该类在任何一方产物里都无法被 keep 到**：
  - 主包：主 mapping 有 `androidx.tracing.Trace.beginSection:130:130 -> reportFullyDrawn` 等**内联帧记录**（Trace 的方法体被内联进调用者），主 dex 0 个 `Landroidx/tracing/Trace;` 类定义 —— R8 合法地把整个类优化掉了，主包自洽。
  - 测试包：测试 dex 0 个 tracing 类定义、测试 mapping 0 条 `androidx.tracing` 条目；测试合并 R8 配置（`mapping/strictOfflineReleaseAndroidTest/configuration.txt`）里也没有 tracing 相关条目，且两次构建日志均无 missing-class 告警 → tracing 在测试 R8 视角是**库类路径**上的"主包运行时会提供"的类（该 AGP 内部装配细节为强推断，标 UNVERIFIED，§八）——引用按原名原样保留，不重写、不打包。
  - 共享依赖不进测试 APK 的旁证（打包排除模型）：测试 dex 有 244 个 `androidx.compose.ui.*` 类定义（测试独有 ui-test 子树）、945 个 `androidx.test.*` 定义，而 `androidx.work.*`=0、`androidx.tracing.*`=0 —— 主包已提供的运行时依赖不在测试 APK 重复打包。
- **触发点**：`r04-k6-logcat.txt:92-97`：主包启动炸了之后，`AndroidJUnitRunner.sendStatus`（测试 dex、被 r04 规则 3 `-keep class androidx.test.** { *; }` 保名）走 `InstrumentationResultPrinter.reportProcessCrash` → `:92` `NoClassDefFoundError: Failed resolution of: Landroidx/tracing/Trace;` ← `:110 Caused by ClassNotFoundException`。`forceEnableAppTracing` 调用点在 `AndroidXTracer`/`ActivityScenario` 路径，属 androidx.test 自身的 tracing 抽象（`androidx.test.platform.tracing.AndroidXTracer` 在测试 dex 有类定义，dexdump `:310672` 附近）。

### 3.2 结论

`androidx.tracing.Trace` 的 CNFE 是**"类在合并 classloader 里不存在"**问题，不是改名问题：keep 规则的作用域是"R8 输入里的程序类"，而该类不在测试 R8 输入、也不在主包产物里。**任何写在 `r04-test-keep.pro` 的规则都修不了它**；唯一确定性落点是让类真实存在于某一 APK（§五.2）。

## 四、修复取舍框架（为什么是这两条规则、为什么不能更少/更多）

判据红线（不放宽）：禁 `-dontobfuscate`、禁 internal 变体；keep 扩充逐条给"消灭哪个具体失败"（门脚本 `tools/ci/check_r04_keep_rules.py` 本会话基线 EXIT=0，改后须仍 0）。

### 4.1 `app/r04-test-keep.pro` 扩一条：`-keep class j$.** { *; }`

**消灭的具体失败**：§二的 `NoSuchMethodError j$/util/g <init>(Ljava/util/Map;)V`（K6 崩溃签名）。

**机理**：两个 APK 都把 desugar_jdk_libs 2.0.3 的 `j$` 类作为程序输入各自 minify（`coreLibraryDesugaring` 配置不参与共享依赖排除——测试 dex 里现存的数百个改名 j$ 类即证），运行时又共享一个 classloader 且测试在前。规则生效后：
1. 测试 dex 的全部 `j$` 类按**原名 + 全成员**存活 → 测试 dex 不再占用任何"主包改名产物名"（`j$/util/g` 在测试 dex 消失）→ 主包对 `j$/util/g` 的引用回落到主包自己的 SynchronizedMap（有构造器）；
2. 同名遮蔽只发生在**原名类**上：主包保了名的 `j$` 类（如 `DesugarCollections`，主 dex 类定义在 `main-apk-classes2.dex.txt:84788`）被测试包的全量副本遮蔽，全量副本是主包收缩副本的**超集** → 主包任何 j$ 成员调用都解析得到。

**为什么是 `j$.**` 全域而不是 `j$.util.**`**：碰撞机制与包无关（`j$/time/*`、`j$/sun/misc/a` 在两 APK 同样各自改名，主/测 mapping 的短名分配互不相同）；本轮只爆 `j$.util` 是因为 instrumentation 路径只走到 `synchronizedMap`。按"消灭本失败类"取全域；`j$` 命名空间是 R8 的保留前缀，不属于生产混淆面。

**为什么成员要 `{ *; }` 而不是仅保类名**：ProGuard/R8 语义（Guardsquare 手册已核）：`-keep` 不带成员块只保类与无参构造器，其余成员仍可被删——只保类名会让遮蔽副本缺主包要调的成员，`NoSuchMethodError` 换个地方复发。

**代价**：仅测试 APK（现 1.1 MB）膨胀——desugar jar 全量入库（jar 约 2 MB，dex 化后增量同量级）。主包零改动、零膨胀。**禁用等价"对称修"**（在 `proguard-rules.pro` 也保 `j$.**`）：会把生产 dex 从"约 30 个按需保留的 j$ 类"扩成全量，生产膨胀换不来测试 dex 已可获得的确定性——拒绝。

**更窄方案为何被拒**：只保 `j$.util.DesugarCollections$SynchronizedMap` 原名（a）不能阻止 R8 把 `j$/util/g` 重新分配给测试侧其他类（改名分配不确定）；（b）只堵一个碰撞点，`j$/time` 等仍埋雷。

### 4.2 `app/proguard-rules.pro` 扩一条：保 `androidx.tracing.Trace` 的三个被引用方法

**消灭的具体失败**：§三的 `NoClassDefFoundError / ClassNotFoundException: androidx.tracing.Trace`（K6 崩溃签名，`sendStatus` 报崩溃路径必经）。

**机理**：合并 classloader 里该类必须存在，唯一能落类的地方是主包（AGP 不把共享依赖装进测试 APK，实测见 §三.1）。规则生效后主包 dex 保留 `androidx.tracing.Trace` + 三个静态方法，测试 dex 的按名 `invoke-static` 解析成功。生产代价：一个 ~1KB 门面类不被内联删除，生产其余混淆面不动（该类主包本就无调用者，保的是"类存在性"）。

**为什么必须在主包文件**：`r04-test-keep.pro` 只作用于测试 dex（其头注释 scope 声明 + AGP 语义），而类不在测试 R8 输入——**keep 不能造出不存在的类**（R8 语义：keep 作用于程序类；库类路径类不物化进 dex）。这是对计划任务 1 前提的**结构性修正**，非可选项。

**建议规则文本**（成员集 = 测试 dex 实测引用的恰好三个签名，§三.1）：

```proguard
# androidx.test (monitor/core: AndroidXTracer$AndroidXTracerSpan, ActivityScenario)
# references androidx.tracing.Trace by name; the test APK does not repackage
# this shared dep (AGP packaging excludes tested-APK-provided runtime deps)
# and the app APK's R8 inlines the whole class away. Keep the referenced
# static methods so the merged instrumentation classloader resolves the name.
# Fixes: NoClassDefFoundError androidx/tracing/Trace (K6 crash signature).
-keep class androidx.tracing.Trace {
    void beginSection(java.lang.String);
    void endSection();
    void forceEnableAppTracing();
}
```

实现轨可选更稳变体：`-keep class androidx.tracing.Trace { *; }`（防 androidx.test 后续版本调用其他 Trace 方法——monitor 1.8.0 现只用这三个）。两者都不触碰判据（仍无 `-dontobfuscate`）。

**文件归属裁定请求**：该规则落在 `app/proguard-rules.pro`（生产规则文件），超出"只扩 r04-test-keep.pro"的原任务表述——属于本研究发现的结构性必要改动，归主会话确认后由实现轨落。

### 4.3 不采纳/需裁定的备选（GitHub 优先纪律下的评分见 §六）

- **`androidTestImplementation("androidx.tracing:tracing:1.2.0")`**：直觉修复，但实测 monitor 的 api 级 tracing 依赖已被排除在测试 APK 外（§三.1）——同坐标依赖大概率同样被"主包已提供"排除，**大概率无效且未验证**；不推荐先行。
- **slackhq/Keeper（Gradle 插件，Apache-2.0，v0.16.1，2026-06 仍活跃，269★）**：自动推断"androidTest 用到但主包被 R8 裁掉"的类并生成 keep——结构性解决本失败类（tracing 这半边）的长期方案，但引入构建插件改动（新依赖、新门），超出本轮最小修复；若 K6 修复后仍见同类漂移，建议作为后续立案。
- **升级/等 androidx.test 出更完整 consumer rules**：上游 #2167 仍 OPEN（§六.3），不可依赖。
