## 2. R1 机制（含「旧序属补救场景」的归属实读）

### 2.1 旧链与根因

旧 `KNOWLEDGE_READ` 只发一次材料查询：

```text
port.readKnowledgeTeachingMaterialsForNodes(
    subject = ...,
    knowledgeNodeIds = top5Ids,
    limit = nodes.size,          // 5
)
```

- `limit = nodes.size` 是**跨全部节点合计**的上限，不是“每节点 1 条”。材料丰沛的节点可以占满多个槽位，其他有材料的节点一条也拿不到。
- 旧 DAO 的 `ORDER BY` 是 `matched.best_role_rank → material_type CASE → title → material_id`，`LIMIT :limit` 在最后。类型 CASE 是 **`MISCONCEPTION_GUIDE` 最先、`CONCEPT_EXPLANATION` 靠后** 的补救序（`KnowledgeTeachingMaterialDao.kt:26-62`，`LIMIT` 在 `:61`）。
- 旧 SQL 的角色秩用 `MIN(CASE role … ) AS best_role_rank` **按 material 聚合**（`:33-43`），不是“该节点自己的绑定角色”；一个材料若绑到多个节点，会用它最好的那个角色参与排序。
- 渲染侧只在“被选中的材料集合”里按节点挑 PRIMARY/第一条；没有材料的节点直接 `orEmpty()`，**不打印任何占位**（旧 `RoomTutorToolRunner.kt:359-361,397-405`，行号口径见审计 `:90-94`）。
- 函数 KDoc 说“每个节点取一条 **PRIMARY 绑定优先** 的材料摘要”（旧 `:379-382`），但实际调用的是上面这条**全局补救序 + 跨节点合计 LIMIT** 的查询。**意图与查询语义不一致，这就是 R1 的机制根因**（机制复核 `:42`）。

旧链的三个生产消费方（机制复核 `:55-63`）：

| # | 调用点 | 用途 | 是否依赖旧序 | 本批裁定 |
|---:|---|---|---|---|
| 1 | `core/data/.../knowledge/RoomTutorTeachingReferenceRepository.kt:26-30` | 讲题参考 / leech 重教的 `TutorTeachingReference`；`limit = MAX_TEACHING_MATERIAL_CANDIDATES = 1024` | **是** | **零改**；顺序进请求指纹，DAO CASE 与该文件的 `reTeachPriority` 有逐值一致契约 |
| 2 | `core/data/.../study/StudyReviewPlannerService.kt:661-665` | `quizAbleScopeNodes`：判断哪些节点有可出题材料；`limit = MAX_KNOWLEDGE_QUIZ_SCOPE_MATERIALS = 64`（`:866`） | 否（只用存在性与 materialId 字典序） | **零改**；但它同样受跨节点合计 LIMIT 影响，属同类遗留 |
| 3 | `core/data/.../study/RoomTutorToolRunner.kt:388-392` | `KNOWLEDGE_READ` 的“绑定材料摘要”；`limit = nodes.size`（最多 5） | 否，但正是受害者 | **本批唯一切换点**：旧调用被移除，改新 port |

### 2.2 「旧序属补救场景」的归属实读

这一条是本批机制判断的核心，逐项读到的证据如下：

1. **DAO 自己把顺序绑到补救权威**：`KnowledgeTeachingMaterialDao.kt:15-24` 明写“按（绑定角色 → **重教类型优先级** → title → material_id）”，并写“**类型 CASE 必须与 `TutorTeachingReferenceSelector.reTeachPriority` 逐值一致**”；语义依据是 `docs/research/leech-remediation-research.md` R5/R6。
2. **`reTeachPriority` 的 KDoc 明说这是重教顺序**：`RoomTutorTeachingReferenceRepository.kt:50-72` 写“**重教材料的类型优先级**”、spec §2.16“强制注入 teaching_material 重教”；`MISCONCEPTION_GUIDE` 0 / `WORKED_EXAMPLE` 1 / `METHOD_MODEL` 2 / `DERIVATION` 3 / `CONCEPT_EXPLANATION` 4 / `REPRESENTATION_GUIDE` 5 / `COMPLETE_SOLUTION` 6（`:73-81`）。理由引 Metcalfe 2017/2025、Bokosmaty/Sweller/Kalyuga 2015 等**错误纠正/例题效应**研究；且该顺序**进请求指纹**（`:56-58`），是可观察行为。
3. **研究文档把语义限定在补救/重教**：`docs/research/leech-remediation-research.md:288-290` 的 R4/R5/R6 是“leech 且掌握度低时强制注入、解释错误推理、优先 `WORKED_EXAMPLE`/`MISCONCEPTION_GUIDE`”；这不是通用讲解场景。
4. **机制复核的结论**：`build/agent-batch23/baseline/mechanism.md:12` 明写“**旧 SQL 的顺序是‘错题补救（leech 重教）’语义，不是通用讲解语义**”；`:40` 写“这组语义只在**错题补救/重教**场景成立”。

**归属裁定**：

- 旧序**本身没有错**，它属于补救消费方 **#1**（讲题参考 / 重教）；**#2** 虽也走旧读口，但**不依赖旧序**（只用存在性与 materialId 字典序），它的问题是同类的跨节点截断，不是顺序。**不能改旧 SQL、不能改 `reTeachPriority`、不能把旧 `limit` 语义改成“每节点一条”**；否则会改变 #1 的顺序与请求指纹、#2 的截断集合（机制复核 `:67-71`）。
- 失败发生在**把补救 API 当作通用讲题 API 使用**（#3）：`KNOWLEDGE_READ` 需要的是“每个节点得到一条教学材料”，旧查询给的是“全局按补救序取前 5 条”。因此修复必须是**新增专用方法 + 只切换 #3**，不是改旧方法。
- **两层建议的差异要如实记录**：机制复核 §2.2（`:154`）曾建议“新方法沿用旧序，只修每节点一条”；预注册 §2.2（`:127-138`）随后把**教学优先序**冻结为出数前口径（`CONCEPT_EXPLANATION → … → COMPLETE_SOLUTION`），并明确“这是使用面顺序，不是补救顺序”。最终实现按**预注册**执行；旧序仍留给补救消费方。两套顺序**并存、不互相写回**（DAO 新方法 KDoc `:73-76`；Port KDoc `:141-145`）。
- 因预注册把“无材料显式标注”纳入本批（§2.1），而审计 R1 的归属把“模型可见形态”标为**契约侧**（审计 `:70`），本报告把它登记为**预注册授权的契约可见变更**，不当作纯本线改动（§9）。

### 2.3 新取数形状（实现实读）

链路：

```text
RoomTutorToolRunner.nodeMaterialSummaries
  → KnowledgeReadPort.readBestKnowledgeTeachingMaterialPerNode(subject, nodeIds)   // 新口，无默认实现
  → RoomStudyDatabase.readBestKnowledgeTeachingMaterialPerNode(...)               // override
```

新 SQL（`KnowledgeTeachingMaterialDao.kt:81-126`）：

- **相关子查询 + `LIMIT 1`**，不用窗口函数；因为 `minSdk = 23`（`core/database/build.gradle.kts:14`）且用 framework SQLite，`ROW_NUMBER() OVER` 在 API 23 不可用（预注册 `:61`）。
